* 阻塞提示（echo area）

心跳检测到主线程阻塞（漂移超过 =el-chronos-block-threshold-ms=，默认 2000 ms）时，
事件**始终**写入 =slow_events=（=kind="block"=）并出现在 =el-chronos-report= 与
Web 页面的阻塞列表里；=el-chronos-collect-notify-blocks= 只控制**要不要提示**：

**两条与提示相关的口径**（v3）：

- 本开关只管 **block 档**。亚秒级的 drift（500–2000 ms，落 =hourly_drift= 小时聚合）**从不发提示**：
  亚秒级不配占用 echo area，且它默认就在报告 / Web 的「阻塞事件」节里可见。
- block 只记**命令外**停转（命令执行时间被 =--finish= 的基线重置切出 gap），因此「某条命令执行
  期间卡了 3 秒」不会产生 block 提示 —— 那条命令自己在「慢命令」里。

| 取值 | 行为 | 适用 |
|---|---|---|
| =nil=（默认） | 完全不提示：不占 echo area，也不写 =*Messages*= | 默认。提示会盖住 minibuffer 候选、打断正在进行的输入与补全 |
| =messages= | =message= 被 =(let ((inhibit-message t)) ...)= 包住：只写 =*Messages*= 历史，不占 echo area | 想事后翻日志、又不想被打断 |
| =t= | 真的在 echo area 显示「el-chronos：主线程阻塞约 N ms（已记录）」 | 调参 / 复现卡顿时需要即时可见 |

「echo area 没出现提示」**不代表没记**——查库最快：

#+BEGIN_SRC sh
sqlite3 -readonly "file:$HOME/.emacs.d/.local/state/chronos/chronos.sqlite?mode=ro" \
  -header -column "select ts, round(duration_ms) dur, context_json from slow_events \
                   where kind='block' order by ts desc limit 20;"
#+END_SRC

（=ts= 是毫秒时间戳，用 =date -d @$((ts/1000))= 换算；=context_json= 里的 =mode= 是
判定时刻的 major-mode，可据此定位当时在哪个 buffer。）

* 命令外停转（drift）与调档指引

**drift 是什么**：主线程在**命令之外**停转 **500–2000 ms** 的按小时聚合（表 =hourly_drift=，
每会话每小时一行：次数 / 累计 / 最坏）。超过 2000 ms 改记 =slow_events(kind='block')= 明细，
两档互斥。**命令内**的停转不进 drift —— 它在 =commands= 里有精确 =duration_ms=，
两表**不可相加、也不该相加**（不相交集合：命令间隙的停转 vs 命令总耗时）。

**两个相关 defcustom**（硬约束：drift 阈值必须 **小于** block 阈值、且**大于**心跳间隔 × 1000）：

| 变量 | 默认 | 含义 | 调档含义 |
|---|---|---|---|
| =el-chronos-drift-threshold-ms= | =500= | drift 档最低记录阈值（毫秒） | 上调 → drift 变少、只剩更明显的停顿；下调 → 更灵敏但小时行更密（更「噪」） |
| =el-chronos-block-threshold-ms= | =2000= | block 档（明细）阈值 | 一般不动；drift 阈值必须低于它 |
| =el-chronos-heartbeat-seconds= | =0.25= | 心跳间隔 | 决定两档的**高估上界**（= 一个间隔）与 drift 的检出下界（= 阈值 − 一个间隔） |

**调档指引（可执行）**：

1. **上线先跑一周再动**（默认值不动）。真实频率未知：batch 只能注入人造延迟，量不出真实
   工作负载下 500 ms–2 s 停转的发生率，因此 500 ms 是估计值，不是实测最优。
2. 观察期结束后看两个数：`select sum(count), max(max_ms) from hourly_drift;`。
   - 每小时行数与次数**过多**、噪声感强 → 把 =el-chronos-drift-threshold-ms= 上调到 **800–1000**；
   - 想看见 0.3–0.5 s 的卡顿 → 下调到 **300**，但**不要低于心跳间隔**（=250=）：
     `阈值 < 250` 时每一次正常心跳间隔都可能被判成 drift，只会把噪声灌进库。
3. 觉得自己机器上 timer 唤醒开销明显（笔记本电池、低功耗设备）→ 把
   =el-chronos-heartbeat-seconds= 回调到 **0.5**：开销约减半，但 block / drift 的**高估上界升到
   500 ms**、drift 检出下界相应上移。
4. 代码里**不做断言**（运行中可改），所以上面两条硬约束由你自己遵守。

#+BEGIN_SRC elisp
;; 想更灵敏：只记命令外 ≥300 ms 的停转（心跳仍 250ms，勿低于它）
(setq el-chronos-drift-threshold-ms 300)
;; 觉得太吵：只记 ≥1 s 的命令外停转
(setq el-chronos-drift-threshold-ms 1000)
;; 低功耗设备：把心跳拉回 500ms（高估上界随之升到 500ms）
(setq el-chronos-heartbeat-seconds 0.5)
#+END_SRC

**250ms 心跳的开销**：实测相对开销 **+0.0357%**（[[file:architecture.org][docs/architecture.org]]
「实测结论 13」；噪声地板 ±0.0003% 的 119 倍，距 0.5% 预算余 14 倍）。**但该数字是在
=emacs -Q --batch= 下测的：GUI 主循环未实测**（batch 无 redisplay、无输入事件队列，唤醒路径更短），
只能作为**上界估计**使用；GUI 侧若观感异常就按上面的第 3 条回调。

* 启动分解的物理边界（重要：不是 bug）

**观测器无法观测自己被加载之前发生的事。**

- 若用 =emacs-startup-hook=（或任何**启动结束之后**的时机）开启 mode —— 本机 =thomas-emacs= 就是
  =(add-hook 'emacs-startup-hook #'el-chronos-mode)= —— 启动分解**只含 =mode-start= 一个锚点、
  没有任何包加载明细**。这是物理边界，不是 bug，也不是采集失败。
- 事实依据：=startup.el= 第 1707 行先 =(setq after-init-time (current-time))=、第 1708 行才
  =(run-hooks 'after-init-hook)=，两行都在 init 文件加载**之后**执行。所以 =collect-start= 执行时
  启动已经收尾，采集器**故意一个启动钩子都不挂**（否则此后你每次 =require= / 打开文件触发的 load
  都会被记成「启动期 load」，把交互期的加载混进启动耗时里，比缺数据更糟）。
- **要完整剖析请把 =(el-chronos-mode 1)= 提前到 =early-init.el=**（例如 =early-init.el= 末尾）：

#+BEGIN_SRC elisp
;; ~/.emacs.d/early-init.el 末尾
(require 'el-chronos)
(el-chronos-mode 1)
#+END_SRC

  此时 =mode-start= 就是「记录起点」，之后的 load 才会进 =startup_phases=。副作用要知道：
  early-init 期间很多设施尚未就绪（=package.el= 未初始化、主题未加载、部分 face 不存在），
  采集器自身必须能降级——项目已按此设计（采集路径全部 =condition-case= 包裹，I6），
  但你的**其他**初始化代码若也搬进 early-init 需自行确认顺序。
- 无论哪种写法，节标题都会如实标注覆盖范围（「自 mode 启动起 X ms / 总 Y ms」），
  **不会**把近似数据冒充全程；包加载耗时本身也是**近似归因**（相邻 =after-load-functions=
  回调的时间差，含前一个文件的收尾）。

* 卸载

三步，顺序不能反（先停观测再删数据，否则会有未 flush 缓冲写回）。

1. **停止观测**： =(el-chronos-mode -1)= —— 清理 timer、hook（含每 buffer 的局部 hook）、
   profiler、未 flush 缓冲（I5 零残留）。确认：=M-: el-chronos--running-p= → =nil=。
2. **移除加载路径**：删掉配置里的 =(require 'el-chronos)= / straight 的 =straight-use-package= 段，
   再从 =load-path= 移除目录；（可选）删除本地 clone。
3. **删除数据**（可选）：删
   =<user-emacs-directory>/.local/state/chronos/chronos.sqlite=（连同同目录的
   =chronos.sqlite-wal= / =chronos.sqlite-shm=）。删除前请先做完第 1 步。

#+BEGIN_SRC sh
# 卸载后彻底清数据（先确认 Emacs 已退出或已 el-chronos-mode -1）
rm -f ~/.emacs.d/.local/state/chronos/chronos.sqlite*
#+END_SRC

不删库也不影响其他功能：下次重新启用会复用同一库继续累积。

* 数据清理

| 操作 | 入口 | 作用范围 | 备注 |
|---|---|---|---|
| 自动 retention | 采集运行中周期执行 | 仅 =commands= / =slow_events=，按 =el-chronos-retention-days=（默认 30 天） | 六张 =hourly_*= 聚合表与两张会话级表（=startup_phases= / =session_meta=）**永久保留**，不参与自动清理 |
| 按日期 purge | =M-x el-chronos-purge=（交互输入 =YYYY-MM-DD=） | 该日期之前的**全部**数据（含六张 =hourly_*= 与两张会话级表） | 输入留空 = 清空全部 **11 张表** |
| 全部 purge | =M-x el-chronos-purge= 后直接回车 | 清空 11 张表 | purge 会顺带补建当前会话行，避免后续写入撞外键（并把它重建行的 =startup_ms= 置 NULL） |
| 回收空间 | =M-x el-chronos-store-vacuum= | =VACUUM=（重写库文件） | 不能在事务内执行；purge 后跑一次可显著缩小文件 |
| 直接删文件 | 关闭 Emacs 后 =rm chronos.sqlite*= | 全部 | 下次启动自动重建空库（=user_version= 3、11 表 + 3 索引） |

#+BEGIN_SRC elisp
(el-chronos-purge (truncate (* 1000 (float-time (date-to-time "2026-09-01 00:00:00")))))
;; => (("commands" . 12345) ("slow_events" . 67) ("hourly_functions" . 890) ...)
(el-chronos-store-vacuum)   ; => t
#+END_SRC

** 何时该 purge

- 库文件明显膨胀（例如开了 =el-chronos-usage-granularity= 为 =file= 一段时间后改回 =command=，
  旧的路径类 =hourly_usage= 行不会被自动清掉——该表永久保留）。
- 换了机器 / 换了工作场景，旧数据的趋势对比已无意义。
- 怀疑数据被污染（例如长时间未联网机器时钟跳变导致的桶错位）。

* 排障

| 症状 | 可能原因 | 处置 |
|---|---|---|
| 启动即告警「SQLite 不可用」，采集被禁用 | Emacs < 29 或编译时缺 sqlite | =M-: (and (fboundp 'sqlite-open) (sqlite-available-p))=；换带 SQLite 支持的 Emacs 构建；观测器本身不阻断 Emacs 启动 |
| =el-chronos-web-start= 抛 =user-error=「端口被占用」 | 8787 已被占用（可能是别的实例或 Windows 侧进程） | =ss -lntH "sport = :8787"= 查监听者；改 =el-chronos-web-port= 后重试。**不自动换端口**是设计（I11：可见失败优于静默漂移） |
| 热点函数里一堆 =unknown= 包 | 函数来自**已删除包的残留 =.eln=**、=eval= 即时定义的临时 snippet（=.yas-setup-*=），或 =symbol-file= 确实取不到源码 | native-comp 的 =.eln= 路径已能反查源码（TD-1 已关闭，实测 96.6% 反查成功），故 =unknown= 现在**只剩这两类边界**。看 =el-chronos-attrib-file= 对该符号的返回值：返回 =.eln= 路径说明反查失败（多半是包已删）；不影响其他统计。需要源码级结论时用 =el-chronos-profile-command= 对单条命令剖析 |
| 采样数一直是 0 / 热点表空 | ① 采样器启动失败（=display-warning=）；② 观测期间**没有真实操作**——纯 =sleep= 不产生 CPU 样本 | ① 查 =*Messages*= 与 =el-chronos-status=；② 正常敲命令 1 分钟后再看（采样是 CPU 采样，阻塞等待期没有 leaf 样本，阻塞要靠心跳 =slow_events(kind='block')= 体现） |
| DB 体积显示得比预期小 | =el-chronos-analysis-db-size= **只统计主文件**，不含 =-wal= / =-shm=；WAL 未 checkpoint 时数据还在 wal 里 | 看总占用：=ls -l ~/.emacs.d/.local/state/chronos/=；随 checkpoint 主文件会长上来；需要立刻收敛就跑 =M-x el-chronos-store-vacuum= |
| 某些 buffer 里的命令完全没被计时 | TD-9 类问题（=pre-command-hook= / =post-command-hook= 在 Emacs 31 起 auto-buffer-local） | 已修复：启动时遍历 =buffer-list= 补挂局部 hook 并由 =buffer-list-update-hook= 增量覆盖；若自造 buffer 仍漏采，确认没有在 =kill-all-local-variables= 之后手动覆盖这两个 hook |
| =total_ms= 与内置 =profiler-report= 的 total 列不一致 | 口径不同：本模块 total 按**栈内去重**，内置报告按每帧累加（TD-10） | 不是 bug。占比与回归判定都用 self 口径；跨工具对比时以 self 为准 |
| echo area 不再弹出「主线程阻塞约 N ms」 | =el-chronos-collect-notify-blocks= 默认为 =nil=（静默），**不是漏记**——事件照旧落 =slow_events(kind="block")= 并进报告 / Web 页面 | 查库确认（见「阻塞提示」节的 SQL）；需要即时可见就把该变量设为 =messages=（只进 =*Messages*=）或 =t=（真 echo） |
| 回归列表里出现看起来「没变慢」的函数 | 回归按 =el-chronos-regression-window-days=（默认 7 天）与自身上下窗口比较，**与页面显示范围无关**；小样本噪声由 =el-chronos-regression-min-samples= 抑制 | 看返回里的 =:current-samples= / =:previous-samples=；嫌噪就提高阈值或最小样本数 |
| 包占比里 =built-in= 占大头（甚至过半） | **正常口径**：Emacs C 原语（=kill-buffer= / =plist-get= / =redisplay_internal= 等）与 GC 采样本就来自内核，2026-10-25 起归 =built-in= 而非 =unknown= | 无需处理；若想看用户配置的开销，按包名过滤掉 =built-in= / =GC= / =unknown= 三行即可。历史数据需 =el-chronos-purge= 后重来才是新口径 |
| 采集健康显示「本期无采集数据」 | **不是故障**：采集器还没写过 =hourly_health= 行（=:rows= = 0），例如刚开始用、或这段时间内没有一次 flush 成功过 | 与「本期无采集异常」是两个不同结论：先确认 =el-chronos-mode= 在跑、=M-x el-chronos-status= 能显示库路径，然后等一个 flush 周期（默认 5s）再看。只读 =:ok-p= 会把「没采集」读成「一切正常」，报告与页面都按 =:rows= 先行分支 |
| =heap_bytes= 恒为 =−= / 为 NULL | **Emacs < 31.1 没有 =garbage-collect-heapsize=**，采集层守卫失败即不采，该列恒 NULL | 正常能力缺口，不是采集失败。=M-: (fboundp 'garbage-collect-heapsize)= 验证；升级 Emacs 后只有**新会话**才有堆值，历史会话永远是 NULL（跨版本混图会出现空洞，按 =sessions.emacs_version= 分组看） |
| 启动分解只有 =mode-start= 一个锚点 | mode 在**启动结束之后**才启用（典型写法 =(add-hook 'emacs-startup-hook #'el-chronos-mode)=） | **物理边界，不是 bug**：观测器无法观测自己被加载之前的事。要完整剖析就把 =(el-chronos-mode 1)= 提前到 =early-init.el=（含副作用说明，见「启动分解的物理边界」节） |
| 报告里没有「命令外停转」数字 | ① 该窗口内确实**没有 500–2000 ms 的命令外停转**（正常，报告会写「本期无记录」）；② =el-chronos-drift-threshold-ms= 被调高（如 1000），落在阈值下的停转本就不记；③ 该窗口内主线程一直有命令在跑（命令内停转不进 drift） | ①③ 无需处理；② 查当前值 =M-: el-chronos-drift-threshold-ms=，需要更灵敏就按「命令外停转（drift）与调档指引」下调（**不要低于心跳间隔**）。直接查库确认有无记录：`select hour_ts, count, total_ms, max_ms from hourly_drift order by hour_ts desc limit 10;` |
| 命令内卡顿没进 drift（「我明明卡了两秒」） | **设计如此**：drift 与 block 只覆盖**命令之外**的停转，命令执行期间的时间被结算时的基线重置切出 gap | 命令内的停转看「慢命令 TOP」节 / =commands.duration_ms=（≥200 ms 的另有一条 =slow_events(kind='command')=）。**两表不可相加** —— 相加会把同一段时长算两次。见「命令外停转（drift）」节 |
| v3 前后 =slow_events(kind='block')= 的量看起来变少了 | **口径变了，不是采集退化**：v3 之前命令内 ≥2 s 停转会**同时**记 =kind='command'= 与 =kind='block'=（双记，TD-11 ③）；v3 起 block 只记命令外停转，命令内那一条不再产生 | 做跨版本趋势对比时**必须按时间点切开**（升级前后分段统计），否则会把「双记消失」误读成「阻塞变少了」。历史行不迁移、不回改 |

* 验证步骤

** 自动化（仓库自带入口，全部走 =emacs -Q --batch=，不碰运行中的 daemon）

| 命令 | 层级 | 内容 | 期望 |
|---|---|---|---|
| =make check-parens= | L1 | 逐 =.el= 文件括号平衡检查 | exit 0，逐个文件打印 =check-parens: <file>= |
| =make lint= | L1 补充 | 字节编译告警检查（输出到临时目录，不污染仓库） | exit 0；有告警即失败 |

* 隐私边界与数据保留

** 记录 / 不记录

| 类别 | 内容 |
|---|---|
| **记录** | 命令名、耗时、GC 耗时、major-mode、项目 **basename**、结果（=ok= / =aborted= / =error=）、函数符号名、函数定义源码路径（仅归因所需）、会话级 =git-head= / =config-sig= 两键（见下「隐私边界补充」） |
| **不记录** | 被操作文件路径、buffer 内容、按键序列、命令参数、剪贴板、环境变量、**配置文件内容**（=config-sig= 只取相对路径 + mtime + size 的 sha1） |

=commands.project= 只存 basename（=file-name-nondirectory= 处理后的目录名），取不到为 =NULL=；
断言：该列不出现 =/=。唯一例外是用户**主动**把 =el-chronos-usage-granularity= 改为 =file=——
此时 =hourly_usage= 会写入被操作文件的绝对路径，且该表永久保留（只能 =el-chronos-purge= 清）。

** 数据保留表

| 表 | 保留 | 清理方式 | 行数上界 |
|---|---|---|---|
| =sessions= | 随 =commands= 一并清理（=started_at= 同口径） | retention / purge | 每启动一次一行 |
| =commands= | =el-chronos-retention-days=（默认 30 天） | 自动 retention / purge | 每命令一行 |
| =slow_events= | 同 =commands= | 自动 retention / purge | 仅超阈值事件 |
| =hourly_functions= | **永久** | 仅 purge | ≤ 24 × 函数数 / 天 |
| =hourly_usage= | **永久** | 仅 purge | ≤ 24 × 维度取值数 / 天 |
| =hourly_stacks= | **永久** | 仅 purge | ≤ 24 × =el-chronos-store-stack-top-n=（默认 200）× 会话数 / 天 |
| =hourly_gc= | **永久**（仅 purge） | 仅 purge | 每会话每小时 ≤ 1 行（与既有 =hourly_*= 同量级，可忽略） |
| =hourly_health= | **永久**（仅 purge） | 仅 purge | 每会话每小时 ≤ 6 行（6 个固定键；同量级，可忽略） |
| =hourly_drift= | **永久**（仅 purge） | 仅 purge（=el-chronos-store--prune= **不碰它**） | 每会话每小时 ≤ 1 行；只在命令外 500–2000ms 停转发生时写入（主键去重 upsert），与 =commands= 的时长**不可相加** |
| =startup_phases= | 随 =sessions= 由 purge 清理 | 仅 purge | **每会话 ≤ top-N + 3 行**（默认 ≤ 53，=el-chronos-startup-top-n= 为 50；=first-idle= 记录时 ≤ 54）—— 比 =sessions= 高两个量级，**频繁重启的机器上会明显增长，是本项目最值得留意的一张表** |
| =session_meta= | 随 =sessions= 由 purge 清理 | 仅 purge | 每会话 ≤ 2 行（=git-head= / =config-sig=，取不到则不写行） |

** 隐私边界补充：=session_meta= 的两个键

=session_meta= 记录两个会话级标记：

- =git-head=：配置仓库的**提交 sha**（含分支解析：读 =.git/HEAD= → loose ref → =.git/packed-refs=
  回退 → detached 裸 sha；任一步失败即不写行）。
- =config-sig=：配置文件的**指纹**，由 =el-chronos-config-watch-globs=（默认
  ='("early-init.el" "init.el" "lisp/init-*.el")=）展开的每个文件的**相对路径 + mtime + size**
  排序后做 =secure-hash 'sha1= 得到。**不含任何文件内容**。

**这两个键可以识别你的配置仓库状态**（用了哪次提交、配置何时改过），属用户可识别信息：
=el-chronos-purge= **会删除它们**（含当前会话行的 meta），所以「泄露」窗口 = 库里还留着那段历史的时间。
不想留就可以随时 =M-x el-chronos-purge=。若连采集都不想有，把 =el-chronos-config-watch-globs=
设为 =nil=（不匹配任何文件 → 不写 =config-sig= 行）；=git-head= 没有开关，由 purge 负责清理。

** Web 的特殊说明

Web 无鉴权；只绑 =127.0.0.1= 仅防 LAN 暴露，**不构成本机访问控制**（WSL2 mirrored 网络下
Windows 侧进程可直连该端口）。定位是「本机自用的只读视图」：默认不启动，用完即
=M-x el-chronos-web-stop=，不要在不可信本地进程或多用户共享环境里长期开着（TD-6）。
