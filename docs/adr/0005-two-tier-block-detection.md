# ADR-0005 亚秒级卡顿采用两档阈值（block 明细 + drift 聚合）

- **状态**：Accepted（已接受）
- **日期**：2026-10-25
- **决策者**：用户（明确要求在 block 明细之外补一档亚秒级可见性，并接受「聚合而非明细」的取舍）
- **关联**：`openspec/completed/add-drift-detection.md`（落地计划）、
  `openspec/tech-debt.md` TD-11（本 ADR 解决其 ①②③ 的主干部分）、
  `docs/architecture.org`「实测结论 10」（阻塞捕获覆盖率）/「实测结论 13」（S1 采集开销）、
  `AGENTS.md` I2 / I4 / I6 / I10、`openspec/decisions.md`

## 背景

心跳采集（`el-chronos-collect--heartbeat`，路径 3）是唯一能在「命令之外」发现主线程停转的
手段。它的判定是一条单阈值比较：`gap-ms > el-chronos-block-threshold-ms`（默认 2000），
命中即向 `slow_events` 写一条 `kind='block'` 明细。

TD-11 记录了实测（2026-10-24，`docs/architecture.org`「实测结论 10」）暴露的四个缺陷：

| 缺陷 | 机制 | 量化 |
|---|---|---|
| **检出下界高** | `gap-ms = 真实停转 + 偏移`，偏移 = 阻塞开始时刻 − 上一次成功心跳时刻 ∈ [0, 1 心跳间隔]。真实停转必须 > 2000 − 偏移 才可能被记 | 真实 > **1.0–2.0s**（相位相关）；实测 B2 的 1.5s 在偏移 450ms 时**漏记** |
| **系统性高估** | 记录值是「到上一次心跳为止的总 gap」，不是停转本身 | 上界 **+1 个心跳间隔（1s）**；实证 1.6s 停转（距上次心跳 973.7ms 处开始）记成 **2576.4ms，+61%** |
| **双记** | 命令内停转 ≥2s 既记 `kind='command'`（精确）又记 `kind='block'`（高估）；而 block 的 `command` 列恒 NULL，没有去重依据 | 实测 A3：command 3000.0 + block 3371.5 |
| **亚秒级零可见** | 上述下界的直接后果 | **命令外**的 <2s 停转（timer 回调里的 GC 92ms、单次大 buffer font-lock 一段、进程过滤器、短同步 IO）在 `slow_events` 里**没有任何痕迹**，只能从 `hourly_functions` 小时聚合间接猜。命令内的同类停转有 `commands` 的精确时长兜底 |

同时，「心跳降频能改善多少」已在「实测结论 13」测掉（2026-10-25）：

| 心跳间隔 | 相对开销 | 判定 |
|---|---|---|
| 1000ms（现状） | +0.00779% | 可测但可忽略 |
| 500ms | +0.01712% | 可接受 |
| **250ms** | **+0.03570%**（净增 +0.0279%，距 0.5% 预算余 **14 倍**） | **开销维度可上**；但该数字是 `emacs -Q --batch` 下测的，GUI 主循环未验证 |

**核心洞察**：心跳降频只把偏移上界从 1000ms 压到 250ms（收窄高估），
**不改变 `gap > 2000` 这条判定** —— 真实 1.5s 的停转在多数相位下依然不记。
要让亚秒级可见，**必须动阈值**。

## 决策

**两档阈值：block（2000ms）保持 `slow_events` 明细，drift（500ms）新增 `hourly_drift`
小时聚合**（**只统计命令外停转**）；**心跳间隔降到 250ms**；
**在 `post-command-hook` 结算后重置心跳基线** —— 命令执行时间被物理切出 gap，
于是「命令内外」的分离**不靠任何判据**，双记被结构性消除。

| 档 | 阈值 | 落点 | 粒度 | 保留 |
|---|---|---|---|---|
| block | `el-chronos-block-threshold-ms` = 2000（**不变**） | `slow_events(kind='block')` | 逐条明细（含归因上下文） | `el-chronos-retention-days`（30 天） |
| drift（**仅命令外**） | `el-chronos-drift-threshold-ms` = **500**（新增） | **新表 `hourly_drift`** | 每小时每会话一行（`count` / `total_ms` / `max_ms`） | **永久**（仅 `el-chronos-purge`） |

```sql
CREATE TABLE IF NOT EXISTS hourly_drift (
  hour_ts INTEGER NOT NULL, session_id INTEGER NOT NULL,
  count INTEGER NOT NULL DEFAULT 0, total_ms REAL NOT NULL DEFAULT 0,
  max_ms REAL NOT NULL DEFAULT 0,
  PRIMARY KEY (hour_ts, session_id));
```

### D1 两档互斥，判定链三步（两个门）

`el-chronos-collect--heartbeat` 内按顺序：

1. **抑制门**：`--suppress-block-p` 为真 → 只推进基线、不判定（现状不变）；
2. **兜底门**：`--pending-p` 为真 → 跳过判定（只推进基线）。它是兜底而非主判据：
   命令中途让出主线程（`sleep-for` / 同步 IO / 等待输入）时心跳会真的跑起来，此后命令内
   若再停转，`gap` 会跨过命令边界进入下一个窗口；
3. **判定**：`gap > block-threshold` → 记 block 明细（`command` = nil）；**否则**
   `gap > drift-threshold` → 累加 drift 小时桶；都不满足 → 什么都不做。

两档共用同一条判定路径与**同一对门** —— 任何「只给一档加门」的写法都会造出一个能被
静默污染的档位。

阈值与偏移的合成结果（**必须这样向读者解释，否则 500ms 会被误读成精确下界**）：

| 档 | 真实停转被记的下界 | 记录值的高估上界 |
|---|---|---|
| block | 2000 − 偏移 ∈ [1750, 2000]ms | **250ms**（原 1000ms） |
| drift（**仅命令外**） | 500 − 偏移 ∈ [250, 500]ms | 250ms（`total_ms` 每次最多多算 250ms） |
| 命令内（任意时长） | 两档都不记（基线被重置） | — （由 `commands` 精确覆盖） |

**偏移的起点变了**：不再是「上一次心跳」，而是「上一次心跳**或命令结算**中较晚的那个」
—— 因为 `--finish` 也会推进基线。偏移上界仍是 250ms（心跳间隔），故上表区间不变。
| 命令内 500–2000ms | 两档都不记 | — （由 `commands` 精确覆盖） |

### D2 亚秒级走聚合，不走明细

亚秒级卡顿的问题形态是「这个小时 37 次、累计 24 秒、最坏 1.8 秒」，不是「请看第 12847 行」。
把它灌进 `slow_events` 的后果是可量化的：按 1 次/分钟的中等频率估算，一天 1440 行、
30 天保留期 4.3 万行，而 `slow_events` 的既有语义是「重要事件簿」（报告里限 20 行展示，
可逐条点开看栈与上下文）—— 掺入亚秒级噪声会让真正的 3 秒卡顿被埋掉。

`hourly_drift` 的三个列就是回答上述形态的最小集合：`count`（频率）、`total_ms`（累计代价）、
`max_ms`（最坏一次）。**不记时间戳、不记栈、不记命令** —— 定位亚秒级事件本来就要靠同时段的
采样表（`hourly_functions` / `hourly_stacks`），逐条明细提供不了额外信息。

### D3 心跳 250ms

把偏移上界从 1000ms 压到 250ms：block 的高估收窄 4 倍，drift 的检出下界从
「500 + 0~1000 抖动」收敛到「250–500ms」。开销依据见背景表（+0.0357%，余量 14 倍）。
代价与未验证项见「后果」节 —— GUI 侧未实测，且用户已明确拒绝在其主实例上跑探针，
故该数字只能作为**上界估计**使用。

两个 defcustom 的硬约束：`el-chronos-drift-threshold-ms` 必须 **> 心跳间隔 × 1000**
（否则每一次正常心跳间隔都被判成 drift）。代码不做断言（运行中可改），约束写进 docstring
与 `docs/operations.org` 的调档表。

### D4 判定逻辑抽成 `--heartbeat-check`，三处调用：重置 / 补判 / 只重置

把 `--heartbeat` 里的「判定 + 重置」抽成
`el-chronos-collect--heartbeat-check (&optional now)`（无参取 `(float-time)`，供测试注入），
`--heartbeat` 退化为薄壳，然后**三处调用、职责各不相同**：

| 调用点 | 调用形态 | 作用 |
|---|---|---|
| 心跳 timer（250ms） | `--heartbeat-check` | 判定 + 重置：覆盖「两条命令之间迟迟没有下一条命令」的停转 |
| **`--pre-command`**（新增） | `--heartbeat-check` | **补判 + 重置**：在开始新命令计时之前结清「命令外时间」（D4a） |
| **`--finish`** | **纯 `(setq --last-heartbeat (float-time))`**，**不调 check** | 仅重置：丢弃命令内时间。**此处调 check 会让 `gap` 等于刚执行完的命令时长 → 双记立刻复活**（唯一硬禁令） |

`--finish` 的位置（`el-chronos-collect.el:438`，`let`（450–452）之后、清状态 `setq`（454–459）
之前）与三条理由（贴住命令结束时刻 / 早于状态清空 / 在 `when` 之外以覆盖 `aborted` 与
无主命令路径）不变，见落地计划设计 4.2。

#### D4a `--pre-command` 补判：纯重置方案的必需补强

**纯重置方案（只有 timer + `--finish`）有一个按用户行为分布的漏检**：

```
命令外停转 1.2s（timer 回调忙等）→ 心跳被饿死，跑不了
主线程恢复，用户已按键 → Emacs 先执行命令（输入优先于 timer）
post-command-hook → --finish 重置基线 = now → 心跳补跑只看得到 250ms
⇒ 那段 1.2s 永久消失
```

而「卡顿结束后立刻继续敲键」恰是**最常见的用户行为**，所以这条不能靠「概率低」带过。
补强：在 `--pre-command`（`el-chronos-collect.el:378`）里也调一次 `--heartbeat-check` ——
命令开始前是「命令外时间」的**最后一个可观测时机**（错过它，timer 已经饿死、`--finish`
又会把整段吞掉）。

**落点定死**：`(--finish 'aborted)`（417 行）**之后**、`(if (null name) …)`（418 行）
**之前**。理由：

1. 必须在 aborted 结算**之后** —— 否则 `--pending-p` 仍为 t，兜底门跳过判定，补判白跑；
2. 必须在 `--command-start` 赋值（426）之前 —— 补判度量的是「命令开始之前」的时间；
3. 放在 D1 双跑守卫（412–415）之外 —— 守卫命中表示同一条命令被双跑、没有真实间隙，
   补判本来也不会记录任何东西。

**aborted 结算耗时会被计入该次 `gap`（明确接受）**：`--finish` 的写入开销（`attrib-context`
/ `--current-stack` / `--safe-apply`）落在 `gap` 里，量级 µs–ms（远低于 500ms 阈值），
且只在 C-g / 异常中断路径发生。这是有意接受的粗化 —— 换成「先补判再结算」反而会让判定
完全失效（兜底门）。

**三处共享一个基线不会重复记录**：`--last-heartbeat` 只有一个，谁先跑谁推进。间隙内主线程
空闲时 timer 每 250ms 推进一次，`--pre-command` 看到的 `gap` ≤250ms 不记；只有间隙内主线程
真被占住（timer 跑不了）时 pre 才看到大 `gap` 并记一条。互斥由**共享基线 + 单一判定函数**
天然保证，不需要额外去重。

**机制**：心跳的 `gap` 是「本次触发 − 上次触发」。基线在每条命令结算时被推到「命令刚结束」，
于是**命令执行期间的时间不进入任何 gap** → block / drift 只能覆盖命令之间的时间。
一句话：把「命令内外」从**判定问题**降级为**基线位置问题**。

**落点为什么是这里**（读码后的三个理由，对应现状 450–452 行的 `let` 与 454–459 行的 `setq`）：

1. **贴住命令真实结束时刻**：结算里有 `attrib-context` 归因、`--current-stack` 取栈、
   多次 `--safe-apply` 写库；越往后放，这些开销越会被排除在 gap 之外。
2. **早于命令状态清空**：若结算过程中心跳被触发（写库可能产生 IO），此时 `--pending-p`
   仍为 t → 兜底门跳过判定；基线已是 `now`，解除兜底后也不会把结算耗时算成 gap。
3. **在 `(when (and (numberp start) name) …)` 之外**：`aborted` 路径（`pre-command-hook`
   里结算上一条）与「无主命令」路径**同样重置**。否则 aborted 会把「上一条命令 + 命令间隙」
   整段留给下一次心跳，重新引入命令内时间。

**与 `--pending-p` 兜底门的分工**（两者不可互相替代）：

| 手段 | 覆盖 | 作用 |
|---|---|---|
| 重置基线 | 正常路径（命令正常 post 结算） | 主判据：命令时间根本不进 gap |
| `--pending-p` 跳过判定 | 命令中途让出主线程后又在命令内停转 | 兜底：拦住跨命令边界的 `gap` 泄漏 |

**代价（必须在文档与 tech-debt 里写明）**：若「命令外停转结束」与「下一条命令结算」发生在
同一轮事件循环（主线程恢复后用户恰好有输入待处理），重置会先发生 → 那段停转**整段漏记**。
这是「用重置换掉判据」的对价；缓解方案（重置前先补判一次心跳）会让判定逻辑出现在两处，
本期不做。

**为什么优于「命令归属判据」**：后者用一个比较（反推 `gap` 起点 vs 命令结算时刻）同时驱动
两个输出（`command` 字段 + drift 准入），没有可观测的中间量 —— 时间单位或边界写错时数据
看起来完全合理，**误判窗口 ≤250ms**（一个心跳间隔），且错法静默。重置基线没有判据可错。
**因此 `block.command` 保持 nil**：block 只记命令外停转，没有命令可归因；
「为了字段有信息」去回填上一条命令名会把命令外停转误导成某条命令内的停转。

### D5 schema v3 与迁移链

`user_version` 2 → 3，新增一张表、一条 upsert（`count` / `total_ms` 累加、
`max_ms` 取标量 `MAX`）、purge 扩到 11 表（`hourly_drift` 按 `hour_ts` 删，
位置在 `hourly_health` 之后、`sessions` 之前）；`--prune` 不动它（小时聚合永久保留）。

**迁移链必须是链式的（本 ADR 记录的关键实现约束）**：S1 的 `--migrate` 是
「`(< from-version 1)` → 全量建表」+「`(= from-version 1)` → v2 脚本、版本置 2」两个互斥分支。
只追加一个 `(= from-version 2)` 分支会让 **`from-version = 1` 的库**走完 v2 后停在版本 2，
`--migrate` 却返回 t → 库缺 `hourly_drift` → 本次会话所有 drift 写入 `no such table` →
flush 失败、丢本批、只留限流告警（静默降级型缺陷）。

**定案写法（用户裁决 A）：局部 `version` 变量逐级推进**

```elisp
(let ((version from-version))
  (when (< version 1)
    (el-chronos-store--ensure-schema db)              ; 建全 11 表并把 user_version 置 3
    (setq version el-chronos-store--schema-version))  ; ← 必须同步为 3，不是 1
  (when (= version 1) ...v2... (sqlite-pragma db "user_version=2") (setq version 2))
  (when (= version 2) ...v3... (sqlite-pragma db "user_version=3") (setq version 3))
  (sqlite-pragma db (format "user_version=%d" version)))
```

- **`--ensure-schema` 的交互是唯一陷阱**：它把 `user_version` **无条件**置为当前常量（3），
  所以那次调用返回后库已是最新，而局部 `version` 仍停在原值。三种结局只有一种可接受：
  留在 **0** → 末尾 pragma 把最新库标成版本 0（下次又走一遍迁移，版本号长期失真，禁止）；
  置成 **1** → 版本号正确但 v2 / v3 脚本各多跑一遍（幂等，语义混乱）；
  置成 **`--schema-version`（3）** → 后续分支自然不触发 —— **采用这一种**。
- 每条迁移步骤内部各自 `BEGIN` / `COMMIT`，失败时 `ROLLBACK` 仍走外层既有回滚路径。
- 守门用例三条（计划 T1）：v0 新库一次到 v3（并断言 v2/v3 脚本未被额外执行）、
  v1 老库一次到 v3 且 `hourly_drift` 存在、v2 库到 v3。

### D6 自观测抑制口径：drift 判定必须在 `--suppress-block-p` 之内

报告与 Web 的重查询不得被记成「待排查的卡顿」（既有三条理由：抑制变量、抬阈值、重置基线）。
drift 与 block 同级，判定必须写在同一个 `(unless (bound-and-true-p
el-chronos-collect--suppress-block-p) ...)` 之内。**抑制宏不需要改动** ——
第 2 层是 `let` 动态绑定 `el-chronos-block-threshold-ms`，只在 BODY 执行期间存在；
BODY 之后运行的那次心跳看不到 `--suppress-block-p`，但第 3 层重置基线后
`gap ≈ 心跳间隔 < drift 阈值`，天然不记。真正起作用的落点是判定位置，不是阈值抬升。

**D4 新增的 `--finish` 重置不替代第 3 层**：渲染期间不会有命令结算，抑制宏必须自己重置基线；
两个重置点触发条件互斥（一个在 BODY 收尾、一个在命令结算），语义幂等、互不冲突。
**不要**因为「多了一个重置点」而删掉第 3 层 —— 那会让一次几秒的报告生成变成一条巨型
block/drift 事件。

### D7 drift 只覆盖「命令外停转」

`hourly_drift` 的语义**收窄**为：**「主线程在命令之外停转 500–2000ms 的聚合」**。

- **排除机制不靠判据**：命令内停转不进 drift，是因为 D4 让命令时间根本不进入 `gap` ——
  不是靠「反推 gap 起点 / 维护最近命令」这类判定。
- **为什么这样更干净**：命令内的 0.5–2s 停转**本来就可观测**（作为慢命令进 `commands`，
  ≥`el-chronos-slow-command-threshold-ms` 默认 200ms 时另进
  `slow_events(kind='command')`）；真正的空白只有**命令外**（timer 回调、进程过滤器、
  `redisplay`、GC）。把 drift 限定在命令外，既补上真空白，又不在两个口径里重复记账。
- **推论（必须写进文档）**：`hourly_drift` 与 `commands` 的时长**不可相加、也不该相加**
  —— 它们是两个不相交的集合（「命令间隙的停转」vs「命令总耗时」）。
  任何「总卡顿 = 慢命令 + block + drift」的求和式都是错的。
- **关闭 TD-11 缺陷③（双记）**：block 也只覆盖命令外停转（同一机制的副作用），
  因此「命令内 ≥2s 停转既记 command 又记 block」的历史行为**终结**；
  block 的时长与 `commands` 同样不可相加。

## 备选方案与被否决原因

| 替代方案 | 描述 | 否决原因 |
|---|---|---|
| ① 直接把 block 阈值降到 500ms | 不动 schema，把 `el-chronos-block-threshold-ms` 默认值改成 500，让亚秒级直接进明细 | **明细表爆炸**：500ms 级停转按 1 次/分钟估算一天 1440 行、30 天 4.3 万行，`slow_events` 从「重要事件簿」退化为「噪声日志」，报告 20 行展示区被亚秒级记录占满；且这些行带 `stack_json` / `context_json`，行宽远大于聚合行。降阈值同时意味着 `count` 语义漂移（用户对 `slow_events` 的既有预期是「值得看的卡顿」） |
| ② 复用 `hourly_usage` 记 drift | 不加表，用既有 `(hour_ts, dimension, key)` 聚合，`dimension='drift'` | **缺 `max_ms`**：`hourly_usage` 只有 `count` / `duration_ms`，回答不了「最坏一次多久」，而 max 恰恰是亚秒级卡顿最需要的读数（平均值被大量小停顿稀释）；且 `hourly_usage` 的语义是「用法统计」（命令/mode/project 的频次与耗时），把停转塞进去会让该表的读者（热力、用法排行）需要额外过滤，**污染语义** |
| ③ drift 也记 `slow_events` 明细 | 加 `kind='drift'`，与 ① 只差在不动 block 阈值 | 同 ① 的膨胀与语义退化；另外会**破坏 `kind` 的判据**：`slow_events` 现有查询（阻塞事件列表、报告节、`/api/blocking`）都按 `kind` 分类，多一个高频 `kind` 会让所有既有查询的默认结果集被稀释，需要逐个加过滤 —— 改动面反而比新表大 |
| ④ 只降心跳（250ms）不动阈值 | 只改 `el-chronos-heartbeat-seconds` 默认值，零 schema 改动 | **只解决高估，不解决检出下界**：`gap > 2000` 判定不变，真实 1.5s 停转仍需 > 2000 − 偏移（偏移上界从 1000ms 降到 250ms，即需 > 1750ms）才被记。亚秒级（<1.75s）依然完全不可见 —— 而亚秒级正是本条要解决的问题。这是成本最低但收益也最小的方案，只作为本方案的一部分（D3） |
| ⑤ 对 drift 也做采样明细（按概率丢弃，保留一部分行） | 以 1/N 采样率把 drift 事件写进明细表，兼顾分布与体量 | **丢分布信息且要额外决定采样率**：采样后的 `count` 不是真实次数（要么放大估计、要么另存计数），`max_ms` 会因丢弃而系统性偏小（最坏那一次恰好被丢的概率与采样率成正比）；采样率本身又是一个没有数据支撑的新参数（真实频率未知，见「后果」），等于用一个未知量去标定另一个未知量 |
| ⑥ 不设固定阈值、改成「相对基线」的自适应判定 | 用近期心跳间隔的移动平均当基线，超出 K 倍即记 drift | 观测器不得替用户定义「什么算卡顿」：自适应阈值会让同一次 800ms 停顿在不同时段得到不同判定，趋势与回归结论失去可比性；且移动平均需要额外的窗口状态与清理责任（I5），收益不抵复杂度 |
| ⑦ drift 阈值不暴露成 defcustom | 写死 500ms，少一个配置项 | **真实频率未知**（batch 只能注入人造延迟，用户拒绝在主实例跑探针），500ms 是估计值；写死则用户无法按自己的机器调档。做成 defcustom + `docs/operations.org` 给调档指引，是「在信息不足时把决定权交还用户」的唯一可行做法 |
| ⑧ **保留「命令归属判据」**（反推 `gap` 起点 + 维护 `--last-command-end-ts` / `--last-command-name` 两个 defvar，同时驱动 `command` 字段与 drift 准入） | 不改心跳基线，靠比较判定命令内外 | **一个比较驱动两个输出，错法静默**：时间单位（秒 vs 毫秒）或边界（`<` vs `<=`）写错时，数据看起来完全合理，只是 drift 偏多/偏少；**误判窗口 ≤250ms**（一个心跳间隔），且命令内外的归属本身是**反推**（`gap` 起点可能落在命令边界附近）。额外的 2 个 defvar 还带 I5 清理责任。重置基线（D4）没有判据可错，且让双记**结构性**消失而非事后去重 |
| ⑨ drift 不区分命令内 / 命令外（全部 500–2000ms 的 gap 都记） | 判定链少一步，规则更简单 | **与 `commands` 重复记账**：命令内 0.5–2s 的停转已作为慢命令落库（`el-chronos-slow-command-threshold-ms` 默认 200ms），再记一条 drift 就是同一段时长的第二个口径，读者一旦相加就重复计数（TD-11 缺陷③ 的原样复发）。而命令内的亚秒级**本来就可观测**，drift 的真空白只有命令外 —— 故收窄（D7） |
| ⑩ **只在 `--finish` 纯重置，不做 `--pre-command` 补判** | 少一处调用、少一次每命令开销 | **停转后立刻按键会整段丢失**（D4a 的序列），而这恰是**最常见的用户行为** —— 用户看到卡顿、立刻继续敲键，结果库里什么都没有。timer 心跳在那一刻正被饿死、`--finish` 又会把整段切掉，pre 是唯一剩下的观测点。省下的开销实测可忽略（一次函数调用 + `float-time` + 两个门判定，量级 <1 µs/命令） |

## 后果

**正向**

- **亚秒级从不可见到可见**：500ms–2s 的停转由 `hourly_drift` 承接下来，回答
  「这个小时卡了几次、累计多久、最坏一次多久」——这正是 TD-11 缺陷① 的正面解。
- **高估上界 1s → 250ms**：block 的 `duration_ms` 精度提升 4 倍（实测结论 10 的
  +61% 最坏偏差收敛到最多 +16%），按 block 总时长做的趋势判据整体收缩。
- **双记（TD-11 ③）被结构性消除**（D4 + D7）：命令执行时间被基线重置切出 `gap`，
  命令内停转进不了 block 也进不了 drift —— 它只剩 `commands`（精确 `duration_ms`）与
  `slow_events(kind='command')` 一个口径。不是「事后按 `command` 字段去重」，而是
  **同一段时长只会被记一次**。
- **没有判据即没有判据错法**：一行 `setq` 替代「反推 `gap` 起点 + 维护两个 defvar +
  一个跨两个输出的比较」。少 2 个 defvar 也少了 I5 的清理责任与「跨会话残留」风险。
- **明细表不膨胀**：new 表是小时聚合（每会话每小时 ≤1 行），与既有五张 `hourly_*` 同量级；
  `slow_events` 的行数、行宽、索引一个字节不变（block 阈值未动）。
- **零第三方依赖不变**：`run-with-timer` / hash table / `sqlite` / SQL 标量 `MAX` 全是内置（I10）。
- **阈值可调且口径写清**：两个 defcustom 及其硬约束（drift 阈值必须 > 心跳间隔）进 docstring
  与调档表，用户可自行在「开销」与「灵敏度」之间取舍。

**负向 / 代价**

- **多一张表**（10 表 3 索引 → 11 表 3 索引）：迁移、purge 顺序、文档同步各多一处风险面；
  schema v3 迁移因此多一条**链式推进**的实现约束（D5）—— 只加 `(= from-version 2)` 分支会
  让 1 号库「迁移成功但仍缺表」，这是静默降级型缺陷，必须有守门用例。
- **心跳默认值是行为变更**：`el-chronos-heartbeat-seconds` 1 → 0.25，timer 唤醒 4 倍。
  开销实测 +0.0357%（batch），但**GUI 主循环未验证**；`CHANGELOG.md` 必须把这条列进
  `### 变更` 并说明可回调。
- **GUI 开销未知**：batch 下唤醒路径更短（无 redisplay、无输入事件队列），实际占比可能略高；
  14 倍余量足以吸收偏差，但这是**推论不是实测**。
- **drift 的真实频率未知**：只能注入人造延迟，量不出真实负载下 500ms–2s 停转的发生率，
  因此 500ms 这个默认值的合适性要等上线观察一周才能校准。
- **block 的历史语义变化（跨版本对比必须注意）**：v3 之前，命令内 ≥2s 停转会记一条
  `kind='block'`（与 `kind='command'` 双记）；v3 之后**不会**。因此库里 2026-10-25 之前的
  `slow_events(kind='block')` 与新数据**口径不同** —— 旧行含命令内停转、新行只有命令外。
  做跨版本趋势对比时必须按时间点切开，否则会误读成「阻塞变少了」。
  `docs/operations.org` 与 `CHANGELOG.md` 必须写明这条。
- **命令内停转只在 `commands` 表可见**：想知道「这段时间所有 0.5–2s 卡顿的总量」必须
  分别查 `commands`（含命令内）与 `hourly_drift`（只有命令外），且**不能相加**。
  这个口径比「含命令内但会重复计数」更难向用户解释，报告与文档必须显式声明。
- **纯重置方案的漏检面已由 D4a 补判解决**：若命令外停转结束与下一条命令结算落在同一轮
  事件循环（卡顿结束后立刻按键），`--finish` 的重置会先发生 → 那段停转整段漏记；
  `--pre-command` 补判在命令开始前把它结清，该序列被覆盖。残余仅两种（D1 双跑守卫命中、
  恢复后执行的不是命令）且都由 timer 心跳兜底，无需额外处置。
  但这也意味着**每一条命令**的 pre-command-hook 多一次调用开销（未实测，见 D3 与 tech-debt）。
- **连续命令流中的累计卡顿不可见（D4 的结构性损失）**：当卡顿分散在几十条 20–50ms 的连续
  命令里（总 1.5s、**单条都不慢**）时，block/drift（命令时间被切掉）与 `slow_events`
  （都 <200ms 阈值）**都看不到**，只有 `commands` 的时间戳密度能反映。判据方案至少能在
  命令内记 block，方案 B 不能 —— 这是「用重置换掉判据」在**能力**上的真实让步，
  必须写入 `docs/architecture.org` 的「已知偏差」并登记 tech-debt。- **两个阈值需要用户理解**：多一个旋钮就多一个配错的机会（drift 阈值 ≤ 心跳间隔时会把
  每次正常心跳记成 drift）—— 靠 docstring 与文档的硬约束声明兜住，不做运行期断言。
- **用例数与测试时长上升**：预计 **+26**（T1 6 / T2 16 / T3 4，200 → 约 **226**，以实测为准）。

**约束（进入不变量语义的解释，不新增不变量）**

I2（阻塞期不依赖 Lisp 回调，心跳只能证明「停了 N 秒」——两档阈值不改变这一点）、
I4（单位：API/DB 毫秒）、I6（采集路径失败降级不抛错：`record-drift` 与心跳判定链都算采集路径）、
I10（零第三方依赖）。**I1–I11 一条不改**。
