* 分层与数据流

分层单向依赖（采集 → 归因 → 存储 → 分析 → 呈现 / 可视化），上层不反向调用下层；任何一层异常都不得向宿主（Emacs 主循环）抛错（I6）。

| 层              | 模块                     | 输入                         | 输出                                   | 副作用                            |
|-----------------+-------------------------+-----------------------------+---------------------------------------+----------------------------------|
| 采集 collect     | =el-chronos-collect.el=   | hook / timer / profiler 回调 | 内存中的事件与小时聚合桶                  | 只读环境、写内存                    |
| 归因 attrib      | =el-chronos-attrib.el=    | 符号名、buffer               | file / package / mode / project 字符串 | 无（缓存 hash table）              |
| 存储 store       | =el-chronos-store.el=     | 聚合结果与事件行               | SQLite 行                             | 唯一允许写盘的一层（I3）             |
| 分析 analysis    | =el-chronos-analysis.el=  | SQL 查询                     | plist 结果集                           | 只读数据库                         |
| 呈现 report      | =el-chronos-report.el=    | plist 结果集                 | org buffer / 导出文件                  | 创建 buffer、按需写导出文件         |
| 可视化 web       | =el-chronos-web.el=       | =analysis= 结果集              | HTTP / JSON → 内嵌 HTML / JS           | 仅监听 =127.0.0.1= （默认关闭、只读） |

数据流： =collect → attrib（补元数据）→ store（小时聚合落库）→ analysis（查询）→ report / web（两种呈现形态，共享同一 analysis 查询层）= 。
=attrib= 是被动依赖（collect 调它补上下文），不被 store 反向调用。

* 采集时序：四条路径

** 路径 1：启动（每会话一次）

1. =after-init-hook= / =emacs-startup-hook= 打点 → 记 =t0= ；
2. 计算 =startup_ms= 、采集 =emacs-version= / =host= / =gc-threshold= ；
3. =store= 插入一行 =sessions= ；
4. 若 =el-chronos-enabled= 为真 → 启动采样器与心跳 timer。

** 路径 2：命令边界（每命令一次）

1. =pre-command-hook= ：
   - 若上一命令仍处于"未结算"状态 → 判为 =aborted= （被 =C-g= 中断），补记一条；
   - 记命令名（=--command-label= ： =real-this-command= 优先，其次 =this-command= ；
     符号取符号名、键盘宏字符串原样、其他非 nil 对象按类型名）、 =t_start= 、
     =gcs-done= / =gc-elapsed= 基线；
   - **命令名两个都取不到（nil）时不开始计时**（旧实现落 =unknown= 无主行）；
2. 命令执行（本观测器不参与，无 advice）；
3. =post-command-hook= ：算 =duration_ms= 、 =gc_ms= 、 =outcome= ；命令名一律用步骤 1
   存下的值（此阶段 =this-command= 已是**上一条**命令，见实测结论 12）；
4. =attrib-context= 补 =mode= / =project= ；用法三维计数自增；
5. 超 =el-chronos-slow-command-threshold-ms= → 追加 =slow_events= 行（含当时栈快照）。

** 路径 3：心跳（每 =el-chronos-heartbeat-seconds=，默认 1s）

1. timer 回调取 =float-time= ，与上次 tick 比较；
2. 漂移 > =el-chronos-block-threshold-ms= （默认 2000ms）→ 记一条 =block= 型 =slow_events= ；
3. 阻塞期间 Lisp 未被调度，因此**栈证据只能来自路径 4 的 SIGPROF 样本**（I2），事后回溯；
4. 更新上次 tick，重新挂 timer。

** 路径 4：采样 tick（每 =el-chronos-sample-window-seconds=，默认 10s）

1. =profiler-cpu-log= 取回本窗口采样（SIGPROF 在 C 层累积，与 Lisp 是否被阻塞无关）；
2. 逐样本聚合：同一函数累计 =samples= / =self_ms= ；依据栈做 total 归属；
3. =attrib= 补 =file= / =package= 维度；
4. 累加进内存中的小时桶（按整点 key 分桶），**不立即写库**；
5. 调 =profiler-cpu-stop= + =profiler-cpu-start=（取用即重置，避免长期累积内存）；
6. =store= 的 flush timer 在小时切换/缓冲达阈值时批量落库。

* 可视化数据流

两种形态（org 报告 / 浏览器 Web dashboard）共享同一 =el-chronos-analysis= 查询层，
不各自写 SQL；任一种不可用都不影响采集与另一种。

** 公共前半段

=页面请求（M-x 或 HTTP GET）→ analysis 查询函数（返回 plist）→ SQLite（只读）→ 结果集=。
analysis 只读数据库，呈现层只消费 plist——因此新增一种呈现形态不需要改采集与存储。

** Web 侧

1. =el-chronos-web-start= 用 =make-network-process :server t :host "127.0.0.1"= 起监听（I8）；
2. 请求 → 路由分发：=GET /= 返回内嵌 HTML/CSS/JS 字符串；=GET /api/*= 调 analysis → JSON；
   =GET /api/export.csv= → CSV；=GET /api/event?id=N= → 单事件完整栈 + 上下文；
3. 前端 JS 定时（默认 30s，可关）轮询 =/api/*= 并本地重绘，无 CDN、断网可用（I10）；
4. =el-chronos-web-stop= 关闭 process 与 buffer，干净释放端口。

** 降级矩阵（I11）

不可用必须**可见**降级，不得静默失败。

| 场景 | 行为 |
|---|---|
| 8787 端口被占用 | =el-chronos-web-start= 明确报错（含端口与改 =el-chronos-web-port= 的提示），不静默失败 |
| sqlite 不可用 | 两种呈现均提示"无数据"，采集侧按既有路径禁用 |

* 启停与降级

- =el-chronos-mode= 为 global minor mode，幂等；停用时按 I5 清理：timer、hook、profiler、未 flush 缓冲。
- sqlite 不可用（Emacs < 29 或编译时缺 sqlite）：=message= 警告并禁用，不报错、不阻断启动。
- 采集路径全程 =condition-case=，失败降级 =unknown= 并继续（I6）。

* 实测结论（2026-10-24，Emacs 31.1，=emacs -Q --batch=）

实现过程中验证的运行时事实，与设计阶段的假设有出入处**以本节为准**（源码注释里也逐条注明）。
这些结论直接决定了几处实现选择，改动相关代码前先读本节。

** 1. profiler 采样日志形态与栈顺序

- =profiler-cpu-log= 返回 **hash table**（键 = 符号 vector，值 = 样本数），不是早期版本的 alist。
  实现里对两种形态都做了兜底（=el-chronos-collect--accumulate=）。
- **栈顺序：=(aref stack 0)= 是最内层（leaf，最近一次求值）**，=(aref stack (1- len))= 是最外层
  （=command-line= / =normal-top-level=）。实测一条长度 16 的栈：
  =[0]=let =[1]=while =[2]=let =[3]=let =[4]=probe-leaf =[5]=+ =[6]=setq =[7]=let
  =[8]=while =[9]=let =[10]=let =[11]=probe-inner =[12]=probe-outer
  =[13]=load-with-code-conversion =[14]=command-line-1 =[15]=command-line=。
- 因此 **self 时间归属取 =(aref stack 0)=**；leaf 常是 =let= / =while= / =+= 这类 subr
  （解释执行的函数把 self 时间落在它们身上），**不做额外过滤**。
- 采集的栈最多保留 40 帧（=--current-stack=），落 =slow_events.stack_json=；报告展示自 leaf
  起最多 8 帧（=el-chronos-report--stack-frames=）。

** 2. =profiler-cpu-start= 已在运行时再调用会抛错（剖析用共享模式）

- 常驻采样已经占着 profiler 时，=el-chronos-profile-command= 不能直接 =profiler-cpu-start=，
  否则抛「profiler already started」类错误。
- 处置：=el-chronos-profile--run= 先判 profiler 是否已启动——已启动则**复用共享模式**
  （取走窗口、跑命令、再取一次差分），未启动才自起自停。因此单命令剖析在观测器运行中也能用。
- 换算：剖析间隔 1ms（=el-chronos-profile--interval-ns= 为 1000000）；样本数很少时用
  =--estimated-interval= 由「样本数 × 实际耗时」反推每个样本代表的时间，避免展示成固定 1ms 的假精度。

** 3. =(backtrace)= 在 Emacs 31 返回 nil（要用 =backtrace-frames=）

- 自 Emacs 31 起 =(backtrace)= 改为「把调用栈打印到 buffer」，**返回 nil**；拿帧列表必须用
  =backtrace-frames=（帧格式 =(求值否 函数 参数表 标记)=）。
- 实现：=el-chronos-collect--backtrace-frames= 用它并保证**不向任何输出流打印内容**
  （否则会污染 =*Messages*= 甚至当前 buffer）。慢事件快照走这条路径。

** 4. =pre-command-hook= / =post-command-hook= 是 auto-buffer-local（TD-9，已修复）

- Emacs 31 起这两个 hook 的 =local-variable-if-set-p= 为 =t=：=add-hook= 不带 LOCAL 时只改
  **默认值**，而任何已留下局部绑定的 buffer（实测 =*scratch*= 被 eldoc 留过局部值）会用局部值
  **遮蔽**默认值 → 该 buffer 内命令完全不计时（静默漏采）。
- 修复为「全局默认值 + 每 buffer 补挂局部值」双路：
  1. =el-chronos-collect-start= 照旧 =add-hook= 全局默认值（新 buffer 未建局部绑定时的来源，
     也是 =el-chronos-mode -1= 后的正常态）；
  2. =--ensure-buffer-hooks= 遍历 =buffer-list=，给未登记的 buffer 建局部绑定（无局部绑定时
     先复制默认值，避免丢掉其他包的默认 hook）后追加本模块两个函数，并 =puthash= 记入
     =--hooked-buffers=（**weak key**：buffer 被 kill 后自动出表）；
  3. =buffer-list-update-hook= 挂同一个 ensure 函数，新建 / 切换 buffer 后增量补挂（已登记者一次
     =gethash= 即返回）；
  4. =el-chronos-collect-stop= 先摘 =buffer-list-update-hook=，再由 =--clean-buffer-hooks= 用
     =remove-hook ... LOCAL=t= 摘局部值，对「摘后已回落默认值」的局部绑定再 =kill-local-variable=
     （不把遮蔽坑留给用户），最后 =clrhash= 登记表。
- 验收：被遮蔽 buffer 内命令计时恢复（batch 端到端捕获到 =move-end-of-line= 事件）；连续 3 轮
  start/stop 无重复挂；stop 后局部值与登记表零残留。

** 5. =buffer-list-update-hook= 会重入，必须加守卫

- 该 hook 在 =get-buffer-create= / 切 buffer 等操作里高频触发，而补挂过程中（=with-current-buffer=、
  =add-hook=、日志）又可能改动 buffer 列表 → 重入。
- 处置：=--ensuring-p= 动态变量做重入守卫，进入即返回；配合「已登记即跳过」，补挂是 O(1) 增量的，
  不会在热路径上退化为全量遍历。

** 6. SQLite 与 JSON 的类型约束

- =sqlite-execute= 的绑定参数**不接受符号**（报 =(sqlite-error "invalid argument")=），
  =json-serialize= 同样不接受符号。
- 处置：落库前 =outcome= / =kind= 与栈里的符号一律转字符串（DB 里仍是 TEXT 的
  =ok= / =error= / =aborted=、=block= / =command=）；=--json-value= / =--json-string= 负责递归转换。

** 7. 命令 error 的识别依赖 advice

- =C-g= 通常**仍会**跑 =post-command-hook=（quit 在命令循环里被捕获），所以这类命令照常结算为
  =ok= / =error=，duration 含卡顿时间——正是目标 #1 要看的。
- =aborted= 只覆盖「上一条命令在下次 =pre= 时仍未结算」，即 =post-command-hook= 被彻底跳过的顶层
  中断（=throw= 到顶层、=top-level= 重启、在 hook 自身或深层原生代码里跳出命令循环）。
- 命令抛错由 =command-error-default-function= 的 advice 标记（TD-8：Emacs 30+ 默认
  =command-error-function= 是 =help-command-error-confusable-suggestions=，内部仍调默认实现，
  实测可用；若用户换成**不委托**默认实现的函数，则 =error= 识别失效）。

** 8. hook 双跑陷阱（D1）

- =run-hooks= 对**列表**值有历史语义：列表中的 =t= 标记表示「跑完本列表**再跑**全局默认值」。
  =pre-command-hook= / =post-command-hook= 自 Emacs 31 起 auto-buffer-local，因此
  「buffer 有局部绑定 + 局部值含 =t=」时，局部值与全局默认值**都会跑**。
- TD-9 的第一次修复在补挂时无条件追加本模块两个函数 → 若某 buffer 既有局部值本身含 =t=
  （=add-hook= 不加 =t=，但第三方包或用户手写局部值可能有），本模块函数既在局部值里又在
  全局默认值里 → 一条命令的 =pre= 跑两次：第一次把上一条结算为 =ok=，第二次发现无待结算命令
  → 补记一条 =aborted= 空记录。表现为命令计数 / 使用频次 / 中断率**约翻倍**，并出现大量
  =duration≈0= 的 =aborted=。
- 两层防护（=el-chronos-collect--ensure-buffer-hooks= 与 =--pre-command=）：
  1. **只在被遮蔽时补挂**：判据 =(not (memq t (buffer-local-value hook buf)))= ——
     局部值含 =t= 时全局已在跑，补挂即双跑；局部值不含 =t= 时才补（此时局部值完全遮蔽默认值，
     不补就是 TD-9 的原始漏采）。判「有无局部绑定」必须用 =local-variable-p=；
     =buffer-local-value= 在无局部绑定时回落全局值，区分不出这两种情况。
  2. **1ms 去重兜底**：=--pre-command= 在 =--pending-p= 为真且
     =(float-time) - --command-start < 0.001= 时直接返回，同一命令不会被记两次；
     即便将来出现新的双跑来源（多个包各挂一次），计数也不会翻倍。
- 残余风险：去重是时间窗比较，两次**真实**相邻命令若相隔 <1ms 会被误合并（人类输入远达不到，
  键盘重复率上限约 30 Hz）。

** 9. 自观测抑制（report / Web）：三层防护 + 心跳侧感知
（本节原名「报告自观测抑制」，更名以纳入 Web 请求处理侧；旧引用按原名检索本文件仍可命中。）

需求：报告生成（首次加载 org + 13 个 analysis 查询）与 Web 请求处理（查询 + 序列化 + 发送，
主线程同步）都不能被自己的 1s 心跳判为阻塞——那是观测者在观测自己，属假阳性。两个入口各有
一个同款宏：=el-chronos-report--without-block-events=（报告）与
=el-chronos-web--without-block-events=（Web 请求），都用三层：

1. 绑定 =el-chronos-collect--suppress-block-p= 为 =t=，collect 侧 =el-chronos-collect--heartbeat=
   用 =bound-and-true-p= 读取：**非 =nil= 时推进 =--last-heartbeat= 基线并跳过阻塞判定**
   （跨模块 =let= 绑定未声明变量会 =void-variable=，故 report 与 web 侧各自先 =defvar= 声明同名变量）；
2. 把 =el-chronos-block-threshold-ms= 临时抬到 60s（=--suppress-block-threshold-ms=），
   兜住抑制变量尚未生效的过渡期，以及 BODY 内部偶发让出主线程时的心跳；
3. **收尾在 =unwind-protect= 清理段把 =el-chronos-collect--last-heartbeat= 重设为当前时刻**。

三层各自负责什么：**BODY 执行期间心跳 timer 基本不运行**（主线程被占），结束后才补跑一次；
那次补跑发生在 BODY 返回、=let= 绑定**已解除之后**，此刻抑制变量已是 =nil=，所以判定照跑——
只有第 3 层（把基线重置到「现在」）能让差值归零，这是它不可省的原因。反过来，若 BODY 内部
有让出主线程的间隙让心跳真的跑了一次，则靠第 1 层：心跳**推进基线 + 跳过判定**，
因此**抑制期间不产生 block 事件，解除绑定后也不补记整段 gap**。

取舍：抑制期间若真发生阻塞也不会被记录。有意接受——报告生成是用户主动触发的重操作，
其耗时属预期行为，不该混进「待排查的卡顿」。

**两处实现的关系**：为保持 =el-chronos-web.el= 零额外依赖（不 require report / collect），
web 侧是**内联重复实现**而非复用 report 的宏；任何一处改动都必须同步另一处，端到端覆盖见
=el-chronos-web-test-suppresses-block-events= 与 report 侧 =--suppress-binding-restored= /
=--report-suppresses-block-event=。

** 10. 阻塞捕获覆盖率（TD-2，2026-10-24 实测）

方法：=emacs -Q --batch -L .= + 独立临时库，=el-chronos-mode 1=，=el-chronos-sample-window-seconds=
调到 1 小时（仅 F 场景用 2 秒）以排除采样 tick 干扰，=el-chronos-heartbeat-seconds= 1、
=el-chronos-block-threshold-ms= 2000（均为默认值）。

**关键方法论**：=sleep-for= / =sit-for= 都会进入 =wait_reading_process_output=，**期间 timer 照常运行** →
用它们注入延迟根本不会让心跳停摆，测不出任何覆盖率（早期用 =sleep-for= 造「阻塞」得到的是全 miss 的
假结论）。真阻塞必须用**纯 Lisp 忙等**（=while= 空转 + =float-time= 判时，不进入任何等待点），
它才是「主线程停转」的等价物；同理真实世界里 =sleep-for= / 同步进程 IO 型「慢」不产生 block 事件。

| 场景 | 真实停转 | 是否捕获 | 记录值 | 误差 | 说明 |
|------|---------|---------|--------|------|------|
| A 命令内忙等 0.3s | 312.7ms（含 hook 开销） | 是 / =commands= 1 行 + =slow_events(kind='command')= | 300.0ms | ≈0（差值即 hook 开销） | 命令计时精确 |
| A0 命令内 =sleep-for= 0.3s | 303.7ms | 是 / 慢命令 | 303.7ms | ≈0 | 对照：=sleep-for= 不是真停转，期间心跳照常触发，无 block 事件 |
| A3 命令内忙等 3.0s | 3020.8ms | 是 / **双记**：command 3000.0 + block 3371.5 | — | block 高估 350.7ms | 同一段卡顿在两种口径里各记一次（见下「双记」） |
| B2 timer 回调忙等 1.5s | 1500.0ms | **否** | — | — | 低于检出下界（本相位偏移 450ms → gap 1950 < 2000） |
| B3 timer 回调忙等 2.5s | 2500.0ms | 是 / block | 2950.5ms | +450.4ms | 预测 2950.4ms |
| B timer 回调忙等 3.0s | 3000.0ms | 是 / block | 3450.6ms | +450.6ms | 预测 3450.6ms（真实 + 上次心跳到阻塞开始的偏移） |

| C 进程过滤器忙等 3.0s | 3000.0ms | 是 / block | 3852.9ms | +852.9ms | filter 在 C 层同步执行，心跳被饿死 |

**误差模型**（用 B / G 的「预测值 vs 实测值」对齐验证，误差 ≤0.2ms）：
记录值 = 真实停转 + 偏移，偏移 = 阻塞开始时刻 − **上一次成功心跳**时刻，取值 [0, 1 心跳间隔 + 抖动]。
因此：
1. 记录值**系统性高估**，上界 ≈ 一个心跳间隔（默认 1s）；最短可高估 61%（G：1.6s → 2.58s）；
2. 检出下界 = 阈值 − 偏移：最差相位（阻塞紧接一次心跳之后开始）需真实停转 > 2s，最好相位约 0.95s；
3. 心跳只能证明「主线程停了 N 秒」：事件里 =command= 与 =stack_json= 恒为 NULL，
   定位靠同一时间窗的 =hourly_functions= / =hourly_stacks= 采样（见实测结论 1 与 F 场景）。

**双记**：命令内停转 ≥ 2s 时既记 =kind='command'=（精确）又记 =kind='block'=（高估 ≤1s）。
两者是不同口径（「这条命令慢」vs「主线程停转」），单看一类不算错；但**把两列相加**当总卡顿时长会重复计数。

**覆盖不到的三类**：
1. 亚阈值停转（<2s，最常见：GC、单次大 buffer font-lock 的一段、短同步 IO）——=slow_events= 里没有痕迹，
   只能从采样表的小时聚合看出来；
2. 真正的**等待型**调用（=sleep-for= / =accept-process-output= / 同步网络）不算停转，心跳照跑，
   因此永远不产生 block 事件（也不该产生——主线程在让出 CPU）；
3. GUI =redisplay= 阻塞在 batch 无法复现，未实测（真实卡顿源通常是 jit-lock / font-lock，已由 D 覆盖）。

**结论**：心跳方案对「≥2s 的纯计算型停转」覆盖率 5/5（A3、B、B3、C、D 全部捕获）；
对「1–2s 区间的停转」是相位相关的部分覆盖（B2 漏、G 捕获）；对「<1s 停转」与「等待型调用」零覆盖。
时长精度为 0…1 个心跳间隔，且恒为高估。

** 11. 采样开销实测（TD-3，2026-10-24 实测）

上次用 =float-time= 墙钟测，受调度抖动 ±9% 完全淹没了效应；本次改用**双层度量**重做：

- 主指标 =get-internal-run-time=（进程 CPU 时间，不受调度等待影响），=float-time= 仅作对照（两者读数一致）；
- **相位级 ABBA**：=profiler-cpu-start= 会把采样定时器重置为「间隔后首次触发」，若每微块
  start/stop 一次，间隔 > 微块时长时**一个样本都采不到**（10/20/100ms 档每块 distinct 栈 = 0）。
  故 profiler 必须**整段相位常驻**，只在相位边界起停；相位顺序 =[关,开,开,关]= 与镜像
  =[开,关,关,开]=，线性漂移与位置效应在组内抵消；
- 负载：栈深 20 的整数**无分配**递归（每微块 ≈7.5ms）。分配型负载（每块 4.2 万个 float）
  会让相位耗时漂到 40%，是上一轮噪声的主因；
- 每档 7 轮取中位数；控制组「间隔 10s」（几乎不采样）给出**噪声地板**。

| 采样间隔 | 开 profiler CPU（中位/轮） | 关 profiler CPU（中位/轮） | 开销（中位） | 样本数/轮 |
|---|---|---|---|---|
| 5ms | 1606.9 ms | 1623.4 ms | **−0.59%** | 304 |
| 10ms（默认） | 1474.3 ms | 1459.8 ms | **+0.98%** | 145 |
| 20ms | 1441.8 ms | 1527.8 ms | **−1.11%** | ~70 |
| 10s（噪声地板） | 1564.4 ms | 1599.0 ms | **−0.66%** | 0 |

**读法**：三个档位的读数全部落在噪声地板 ±0.7–1.1% 内，且与采样率**无单调关系**
（20ms 比 10ms 更负）——说明 10ms 量级的效应低于本机分辨率，不能把 +0.98% 当作真实开销。
决定性锚点来自更高采样率：**1ms 间隔实测 +0.46%**（样本 2887/轮，与理论值吻合）。
单样本成本 = 0.46% × 1.45s ÷ 2887 ≈ **2.3µs**（保守取 1µs 量级），按 10ms 档实测采样率
（145–285 样本 / 0.75s ≈ 200–370 样本/s）外推：**10ms 开销 ≈ 0.02–0.2%**，上限仍低于
0.5% 阈值 → **保持默认 =10000000= ns（10ms）**。

采集模式（=el-chronos-mode= 开/关，含采样 + 1s 心跳 + 存储缓冲 + 命令钩子）：

| 配置 | 开模式 CPU | 关模式 CPU | 开销（中位） | 各轮范围 |
|---|---|---|---|---|
| 深栈负载，10ms | 1717.2 ms | 1652.7 ms | **+1.98%** | −2.31% … +7.37% |
| 深栈负载，20ms | 1646.0 ms | 1660.1 ms | **+0.15%** | 噪声主导 |

同样无法与噪声区分（首轮 +7.37% 是典型的预热/预热后缓存态差异）。

**结论**：10ms 常驻采样开销远低于 0.5%，默认值不动（TD-3 关闭）。两条可复用的方法论：
① =profiler-cpu-log= 返回「栈→样本数」hash table，=hash-table-count= 是 **distinct 栈数**
不是样本数，统计样本必须 =maphash= 求和；② 采样开销类测量必须让 profiler 连续常驻，
按微块起停会因定时器重置而**静默测空**。

** 12. 命令名采集：=this-command= / =real-this-command= 与 M-x 中间态（2026-10-24）

旧实现直接把 =this-command= 转成字符串，取不到就落 =unknown=。线上库实测：=unknown=
107 / 10887 = **0.98%**，全部 =outcome='ok'=、duration 0.17–105ms，集中在
=fundamental-mode=（78 行）、=eca-chat-mode=、=dashboard-mode=，且常**成串**出现
（107 行里 84 行的前一条也是 =unknown=，另有 8 行紧跟 =ebox--hover-event=）—— 说明是一类
「事件未解析为具名命令」的触发，而非用户命令漏采。（注：=ebox--hover-event= 与
=dashboard-mode= 均为 2026-10-24 历史实测采集到的第三方包命令 / major-mode 名，属实测数据
快照，与本仓库可视化层已无 ETAF 依赖无关，见 ADR-0003。）另有 937 行 =anonymous=
（旧实现「`this-command` 非符号」分支，多为 lambda 绑定）。

实测矩阵（Emacs 31.1，=emacs -Q --batch -l= 用 =recursive-edit= 起**真实命令循环**，
逐条打印两个 hook 里读到的值）：

| 场景 | pre-command 次数 | pre 阶段 =this-command= | pre 阶段 =real-this-command= | post 阶段读到的值 |
|---|---|---|---|---|
| 普通自插入键 | 每键 1 次 | =self-insert-command=（符号） | 同左 | **上一条**命令 |
| =M-x <cmd> RET=（实际命令由 =command-execute= 跑） | **1 次**（只有 =execute-extended-command=） | =execute-extended-command= | 同左 | 上一条命令 |
| 外层命令内 =call-interactively= / =command-execute= | 1 次（只有外层命令） | 外层命令 | 同左 | 上一条命令 |
| 前缀键 =C-c p a= | 1 次（只有最终命令） | =p3-foo=（最终命令） | 同左 | 上一条命令 |
| lambda 绑定 | 1 次 | =#[nil ...]=（=interpreted-function=，**非符号**） | 同左 | 上一条命令 |
| 命令内部 =setq this-command= | 不回改本次记录 | 该命令本身 | 同左 | 上一条命令 |

四条可复用结论：

1. **M-x 不会触发两次 =pre-command-hook=**。=execute-extended-command= 内部用
   =command-execute= 跑实际命令，而 =command-execute= **不走** pre/post hook →
   M-x 全程只有一次计时机会（名字是 =execute-extended-command=，线上 61 行）。因此
   **跳过 M-x 中间态 = 让所有经 M-x 触发的命令彻底不被采集**，且 post 阶段补不回来。
   要把它归到实际命令，唯一途径是给 =execute-extended-command= 加 advice（未实施）。
2. **=post-command-hook= 时刻读到的 =this-command= / =real-this-command= 是上一条命令**
   （命令循环在 post 之后才把它们滚进 =last-command=）。故命令名必须在 pre 阶段存下，
   结算阶段不得回读 —— 回读会把上一条命令的名字安到本条上。
3. =execute-extended-command= 在 =command-execute= 之前把 =this-command= 与
   =real-this-command= **双双设成实际命令**（simple.el 原注释：让 =M-x <cmd> RET= 等同于
   =<cmd>= 的键绑定），但改写发生在 hook 之外 → 采集层读不到。
4. =real-this-command= 优先于 =this-command= 的意义在于：后者会被命令自身改写
   （=push-button= 换成回调、=execute-extended-command= 换成实际命令），前者是命令循环
   记下的「用户真正要求的命令」；普通键路径下两者恒等。

修复后（=el-chronos-collect--command-label=）：=unknown= 不再产生（两个变量都取不到时
**不开始计时、不落库**）；非符号命令按类型名落库（=interpreted-function= 等），不再统一
记成 =anonymous=；=commands.name= 恒为可归因的名字。

旧数据（已存在的 =unknown= / =anonymous= 行）**不需要清理**：它们只是分母里的历史噪声，
不影响新数据的正确性，也不影响查询（=top-N= 排序按耗时 / 频次，无名行不会挤占具名行）。
确要收敛可用下面两条 SQL（**未执行**，先备份库文件再跑；=hourly_usage= 里同名的聚合键
也一并清理，否则趋势图仍会画出这两条线）：

#+begin_src sql
DELETE FROM commands     WHERE name IN ('unknown', 'anonymous');
DELETE FROM hourly_usage WHERE dimension = 'command' AND key IN ('unknown', 'anonymous');
#+end_src

| 偏差 | 具体表现 | 原因 / 处置 |
|---|---|---|
