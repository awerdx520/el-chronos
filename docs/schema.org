* 数据库位置与 PRAGMA

- 路径：=el-chronos-db-path=，默认 =<user-emacs-directory>/.local/state/chronos/chronos.sqlite=。
- 迁移：=PRAGMA user_version=（当前 =4=），**只走 =CREATE … IF NOT EXISTS=，一条 =ALTER TABLE=
  都不用**（理由见「迁移 v3 → v4」/「迁移 v2 → v3」/「迁移 v1 → v2」节）。启动时幂等执行，
  可无条件重跑。迁移前先把 DB 文件复制为 =chronos.sqlite.bak=；迁移失败则回滚该文件 +
  =display-warning=，**不破坏原库**（宁可这轮不采集，也不留半迁移状态）。
- =PRAGMA journal_mode = WAL=（读写不互斥）；=PRAGMA busy_timeout = 2000=（实现常量
  =el-chronos-store--busy-timeout-ms=）；=PRAGMA foreign_keys = ON=（打开库即设，
  因此 =purge= 的删除顺序受外键约束，见「purge 的 12 表删除顺序」）。
- 所有时间戳为 epoch **毫秒**（I4）；所有时长为**毫秒**浮点（采样间隔用纳秒，仅存在于内存）。

* 最终 DDL（=user_version= 4，12 表 + 3 索引）

以下与 =el-chronos-store--schema-ddl= 一致，一次批量执行（全部 =IF NOT EXISTS=，幂等）；
=commands= 有外键引用 =sessions=，**建表顺序不能改**。
v2 的四张新表由四个单表 DDL 常量（=--ddl-hourly-gc= / =--ddl-startup-phases= /
=--ddl-hourly-health= / =--ddl-session-meta=）=concat= 进全量串，与增量脚本
=--sql-migrate-v2= 共用**同一批字面量**（两份字面量必然漂移，而漂移的表现是「新库对、旧库缺表」）；
v3 的 =hourly_drift= 同理由 =--ddl-hourly-drift= concat 进全量串，与 =--sql-migrate-v3= 共用字面量；
v4 的 =hourly_resources= 同理由 =--ddl-hourly-resources= concat 进全量串，与 =--sql-migrate-v4=
共用字面量。

** 写路径的 SQL

| 用途 | 形态 | 说明 |
|---|---|---|
| 命令事件 | 纯 =INSERT= | 每命令一行，进缓冲后由 flush timer 批量提交 |
| 慢事件 | 纯 =INSERT= | 只有超阈值 / 阻塞 / 剖析结果才写 |
| 函数聚合 | =INSERT … ON CONFLICT(hour_ts, session_id, function) DO UPDATE SET self_ms = self_ms + excluded.self_ms, total_ms = total_ms + excluded.total_ms, samples = samples + excluded.samples= | 累加而非覆盖 |
| 用量聚合 | =… ON CONFLICT(hour_ts, dimension, key) DO UPDATE SET count = count + excluded.count, duration_ms = duration_ms + excluded.duration_ms= | 同上 |
| 栈聚合 | =… ON CONFLICT(hour_ts, session_id, stack_hash) DO UPDATE SET samples = samples + excluded.samples= | =stack_hash = sha1(stack_json)= 去重 |
| GC 聚合 | =… ON CONFLICT(hour_ts, session_id) DO UPDATE SET gc_count = gc_count + excluded.gc_count, gc_ms = gc_ms + excluded.gc_ms, heap_bytes = COALESCE(excluded.heap_bytes, heap_bytes)= | 计数与耗时**累加**；堆大小**最后一次非 NULL 胜出**（见「六张新表」） |
| 健康计数 | =… ON CONFLICT(hour_ts, session_id, key) DO UPDATE SET value = value + excluded.value= | KV 累加（计数与耗时都是单调量） |
| 启动阶段 | =… ON CONFLICT(session_id, phase) DO UPDATE SET ms = excluded.ms= | 覆盖：同阶段重复打点取最后一次 |
| 会话元数据 | =… ON CONFLICT(session_id, key) DO UPDATE SET value = excluded.value= | 覆盖：同一键只保留当前值 |
| Drift 聚合（v3） | =… ON CONFLICT(hour_ts, session_id) DO UPDATE SET count = count + excluded.count, total_ms = total_ms + excluded.total_ms, max_ms = MAX(max_ms, excluded.max_ms)= | 前两列**累加**；=max_ms= 取**标量** =MAX=（两参数，SQLite 支持），保留本小时最坏单次（见「六张新表」） |
| 资源聚合（v4） | =… ON CONFLICT(hour_ts, session_id) DO UPDATE SET cpu_ms = cpu_ms + excluded.cpu_ms, wall_ms = wall_ms + excluded.wall_ms, rss_kb_max = MAX(COALESCE(…), COALESCE(…)), rss_kb_sum = COALESCE(rss_kb_sum + excluded.rss_kb_sum, rss_kb_sum, excluded.rss_kb_sum), threads_max = MAX(COALESCE(…), COALESCE(…)), load*_sum = COALESCE(load*_sum + excluded.load*_sum, load*_sum, excluded.load*_sum), load_n = load_n + excluded.load_n= | CPU / 墙钟 / 负载和 / 样本数**累加**；RSS 与线程数峰值取标量 =MAX=；可空列一律 =COALESCE= 包住（=nil= 既不覆盖既有非 NULL 值、也不把 =NULL + x= 算成 =NULL=） |

** slow_events（超阈值事件 + 阻塞事件）

| 字段 | 类型 | 说明 |
|---|---|---|
| =id= | INTEGER PK AUTOINCREMENT | 行 id |
| =ts= | INTEGER NOT NULL | 事件时刻 |
| =duration_ms= | REAL NOT NULL | 持续时长 |
| =kind= | TEXT | =block=（心跳漂移） / =command=（慢命令） |
| =command= | TEXT | 相关命令名（block **恒 NULL** —— 只记命令外停转，没有命令可归因） |
| =stack_json= | TEXT | 符号栈快照（JSON 数组，取内层 N 帧）。**=kind='command'= 时恒 NULL**（见下） |
| =context_json= | TEXT | mode / project / gc 等上下文 |

**=stack_json= 对 =kind='command'= 恒 NULL（v4 起的字段语义变更，对外可见）**：命令型慢事件的栈
快照原先是「有值但无意义」——=--post-command= 结算时命令帧已弹出，记录下来的全是采集器自身帧
（=--post-command → --finish → --safe-apply → --current-stack → backtrace-frames=）。命令执行期的
栈**无法在结算时刻事后取得**，因此该字段对 command 类事件不携带信息，现改为写 NULL（实测旧数据
299/299 行全是自身帧）。命令归属请查 =hourly_stacks= 的**同时段样本**（见
[[file:architecture.org][docs/architecture.org]]「已知偏差」）。=kind='block'= 的 =stack_json=
本来就恒 NULL（阻塞期间没有可靠的 Lisp 回调，I2）。**消费该字段的外部脚本会看到差异。**

** hourly_stacks（每小时 top-N 栈样本，火焰图数据基础）

用于火焰图与调用链分析：只保留每小时样本数最高的 N 条栈（=el-chronos-store-stack-top-n=，默认 200），
超限按 =samples= 淘汰，因此行数上界为「小时数 × 会话数 × N」，不会随采样频率线性膨胀。

| 字段 | 类型 | 说明 |
|---|---|---|
| =hour_ts= | INTEGER NOT NULL | 整点（epoch ms） |
| =session_id= | INTEGER | 会话 id。列本身无 =NOT NULL=（DDL 允许 NULL），但**当前实现恒非 NULL**，见下方约束说明 |
| =stack_hash= | TEXT NOT NULL | =sha1(stack_json)=，去重与主键 |
| =stack_json= | TEXT NOT NULL | backtrace 向量数组（JSON），第 0 帧是 leaf |
| =samples= | INTEGER | 该栈在本小时的命中样本数 |

主键：=(hour_ts, session_id, stack_hash)=。

** =session_id= 的「事实非空」约束

DDL 没有写 =NOT NULL=，但当前实现要求它非空，否则 top-N 淘汰会静默失效：

- SQL 的 =NOT IN (SELECT …)= 在子查询结果含 NULL 时整体不成立；主键也把 NULL 当作互不相等，
  同一栈的多次写入会成为多行而不是累加。因此 =session_id= 为 NULL 时「去重 + 淘汰」都不可靠。
- 写入侧：=el-chronos-store--stack-session= 只在能取到会话 id 时返回它；取不到则**跳过本次栈写入**
  并每进程告警一次（=el-chronos-store--stack-skip-warned=）。采集层无会话时（例如单独加载 store
  做测试）也走这条路径。
- 淘汰侧：=--evict-stacks= 对 =session_id= 为 NULL 的分组**跳过淘汰**并告警一次
  （=el-chronos-store--null-session-warned=），不执行有风险的 DELETE。
- 结论：正常运行时所有行都有 =session_id=；看到 NULL 行说明有非正常写入路径，见
  [[file:operations.org][docs/operations.org]]「排障」。

** top-N 淘汰 SQL

每个受影响的 =(hour_ts, session_id)= 分组在**同一事务内**执行（与 upsert 同一个 flush 事务）：

#+BEGIN_SRC sql
DELETE FROM hourly_stacks
WHERE hour_ts = ?1 AND session_id = ?2
  AND stack_hash NOT IN (
    SELECT stack_hash FROM hourly_stacks
    WHERE hour_ts = ?1 AND session_id = ?2
    ORDER BY samples DESC
    LIMIT ?3);                     -- ?3 = el-chronos-store-stack-top-n（默认 200）
#+END_SRC

要点：

- 淘汰按 **=(hour_ts, session_id)= 分组**，不跨会话、不跨小时；因此上界是「小时数 × 会话数 × N」。
- =ORDER BY samples DESC= 保留样本数最高的 N 条；并列时保留哪条未定义（对火焰图无影响）。
- 只在 flush 时对本批涉及的组执行，不做全表扫描。
- 被淘汰的栈在下一次窗口聚合时可能重新写入（它是「本小时 top-N」而非「永久保留 id」）。

* 六张新表（v2 四张 + v3 一张 + v4 一张，逐表字段语义）

（理由见「迁移 v1 → v2」/「迁移 v2 → v3」/「迁移 v3 → v4」）；既有 6 表的列、主键与索引一字未动。
v2 的四张（=hourly_gc= / =startup_phases= / =hourly_health= / =session_meta=）见前四小节，
v3 的 =hourly_drift= 与 v4 的 =hourly_resources= 见本节末（两者口径最容易被误读，
读之前先看它们的「语义限定」）。

** hourly_gc（GC 次数 / 耗时 / 堆大小的按小时聚合）

| 字段 | 类型 | 说明 |
|---|---|---|
| =hour_ts= | INTEGER NOT NULL | 整点（epoch ms） |
| =session_id= | INTEGER NOT NULL | 会话 id |
| =gc_count= | INTEGER NOT NULL DEFAULT 0 | 本小时 GC **次数**，upsert **累加** |
| =gc_ms= | REAL NOT NULL DEFAULT 0 | 本小时 GC **耗时**（毫秒），upsert **累加** |
| =heap_bytes= | INTEGER | 堆大小字节数；**稀疏写入**，多数窗口为 NULL |

主键：=(hour_ts, session_id)=。数据来源是采样 tick 里读 =gcs-done= / =gc-elapsed= 的增量
（与 profiler 采样解耦，profiler 启动失败也照采），堆大小每
=el-chronos-heap-sample-windows= 个采样窗口取一次。

**=heap_bytes= 是「最后一次非 NULL」语义，不是累加、也不是最后写入值**：写入用
=COALESCE(excluded.heap_bytes, heap_bytes)=。理由（必现，不是防御性设计）：同一会话同一小时内
堆采样是稀疏的，其余窗口都写 NULL；若用普通覆盖，一个采样点之后的第一个 NULL 窗口就会把它抹成
NULL —— 该小时最后一次写入恰好是 NULL 时，整小时采到的值全部丢失。这是**每个会话每小时都会发生**
的场景。读法：=heap_bytes= 的时间戳含义是「本行最后一次有样本的时刻」，不是「本行所属小时的整点」；
同一小时内多次采样只留最后一个值，跨小时不携带。

=heap_bytes= 仅 Emacs 31.1+ 有值（采集层用 =(fboundp 'garbage-collect-heapsize)= 守卫），
更低版本该列恒 NULL —— 跨版本混图时曲线会出现**空洞**，应按 =sessions.emacs_version= 分组阅读，
不要读成「内存没长」。

** startup_phases（启动各阶段耗时）

| 字段 | 类型 | 说明 |
|---|---|---|
| =session_id= | INTEGER NOT NULL | 会话 id |
| =phase= | TEXT NOT NULL | 阶段名：3 个确定性锚点、1 个可选锚点，或 =load:<library>= |
| =ms= | REAL NOT NULL | 该阶段耗时（毫秒） |

主键：=(session_id, phase)=；upsert 为 =DO UPDATE SET ms = excluded.ms=（覆盖，同阶段重复打点取最后一次）。

=phase= 的取值分两类：

- **阶段锚点（固定 3 个确定性 + 1 个可选）**：=mode-start= / =after-init= / =startup= 是确定性锚点
  （mode 启动时 =after-init-hook= / =emacs-startup-hook= 若尚未过就挂一次记下来，已过则跳过、不倒填）；
  =first-idle= 是**可选**锚点（仅在能注册 idle timer 时记一次，且**不作为摘钩依据**——idle 时机受用户
  活动影响、不可预期）。
- **包加载明细 =load:<library>=**：内存中保存全部 load 记录，写库前按 ms 降序**截断到 top-N**
  （=el-chronos-startup-top-n=，默认 50）。因此本表每会话行数 ≤ top-N + 3（=first-idle= 记录时 +1）。

口径（**改这里的代码前必读**）：=load:= 行的耗时是相邻两次 =after-load-functions= 回调的
**时间差**，属**近似归因**（差值含前一个文件的收尾逻辑与它触发的钩子执行），不是精确耗时；
且只覆盖 mode 启动之后发生的 load（物理边界见 [[file:operations.org][docs/operations.org]]「启动分解的物理边界」）。

** hourly_health（采集器自监控计数，KV 累加）

| 字段 | 类型 | 说明 |
|---|---|---|
| =hour_ts= | INTEGER NOT NULL | 整点（epoch ms） |
| =session_id= | INTEGER NOT NULL | 会话 id |
| =key= | TEXT NOT NULL | 计数字段名，见下方键名单 |
| =value= | REAL NOT NULL DEFAULT 0 | 本小时该键的量（计数或毫秒），upsert **累加** |

主键：=(hour_ts, session_id, key)=。键名单固定为六个（=store= 侧 5 个、=collect= 侧 1 个）：

| 键 | 含义 | 写入点 |
|---|---|---|
| =dropped-commands= | 因缓冲达 =--max-buffer-items= 被截断而丢弃的**命令事件**条数 | store =--push-event= |
| =dropped-events= | 同上，被丢弃的**慢事件**条数（与上一行按 SLOT 分流，不混计） | store =--push-event= |
| =flush-failures= | flush 事务 ROLLBACK 的次数 | store =el-chronos-store-flush= 的 error 分支 |
| =flush-count= | flush COMMIT 成功的次数 | store flush 成功路径 |
| =flush-ms= | flush 累计耗时（毫秒，=float-time= 差 × 1000） | store flush 成功路径 |
| =sample-misses= | 采样窗口丢失次数（相邻两次 tick 间隔 > 2 × =el-chronos-sample-window-seconds=） | collect =--sample-tick= |

**已知悖论（必然存在，不是 bug）**：flush 失败时无法把失败计数写进库——写库本身就是失败的那件事。
处置是计数留在内存 defvar 里，**下一次成功 flush 时补写**（eventual 语义），滞后上限 = 一次成功 flush
的间隔（库长期不可写时无上限）。因此库里该键的值 + 内存里未上报的差额 = 真实总量。

** session_meta（会话级元数据 KV，覆盖）

| 字段 | 类型 | 说明 |
|---|---|---|
| =session_id= | INTEGER NOT NULL | 会话 id |
| =key= | TEXT NOT NULL | 键名 |
| =value= | TEXT | 键值 |

主键：=(session_id, key)=；upsert 为覆盖（同一键只保留当前值）。当前实际写入的键有两个：

| 键 | 内容 |
|---|---|
| =git-head= | 配置仓库的提交 sha：读 =<user-emacs-directory>/.git/HEAD= → loose ref → =packed-refs= 回退 → detached 裸 sha，任一步失败即取不到 |
| =config-sig= | 配置指纹：按 =el-chronos-config-watch-globs=（默认 ='("early-init.el" "init.el" "lisp/init-*.el")=）展开的 =(相对路径 mtime size)= 列表的 =secure-hash 'sha1=，**不含文件内容** |

**取不到的键不写行**（不写 NULL 值行）：KV 表里的空值没有信息量，且会让「取不到」与「取了但为空」
在查询层变得不可区分。同理，glob 无匹配文件时也不写 =config-sig= 行。两个键都由 =--ensure-session=
在**每会话一次**的冷路径上**直接 =sqlite-execute= 写入**（不走 flush 缓冲），因此立即可见；
**绝不调 git 子进程**（启动期 fork+exec 会阻塞主线程，且违背「观测不干预」）。

采集点在 =--ensure-session= 即「刚插会话行、拿到 id」处，天然满足「只写已有会话行的 id」——
本表无外键，DB 不会替我们挡孤儿 =session_id=。

=session_meta= 采集变更标记（=git-head= / =config-sig=）属**用户可识别信息**，
隐私声明与 purge 覆盖见 [[file:operations.org][docs/operations.org]]「隐私边界与数据保留」。

** hourly_drift（命令外停转的小时聚合，v3）

| 字段 | 类型 | 说明 |
|---|---|---|
| =hour_ts= | INTEGER NOT NULL | 整点（epoch ms） |
| =session_id= | INTEGER NOT NULL | 会话 id |
| =count= | INTEGER NOT NULL DEFAULT 0 | 本小时 drift **次数**，upsert **累加** |
| =total_ms= | REAL NOT NULL DEFAULT 0 | 本小时 drift **累计时长**（毫秒，**高估值**），upsert **累加** |
| =max_ms= | REAL NOT NULL DEFAULT 0 | 本小时**最坏单次**时长（毫秒，**高估值**），upsert 取标量 =MAX= |

主键：=(hour_ts, session_id)=（每会话每小时一行）。

**语义限定（不读这一段必然误读）**：本表记录的是「**主线程在命令之外**停转 500–2000ms 的聚合」，
区间上界由 =el-chronos-block-threshold-ms=（默认 2000）决定 —— 超过即改记
=slow_events(kind='block')= 明细，两档互斥（一次 gap 只进一档）。

三个列各自回答一个问题：=count= 是**次数**（这个小时卡了几次）、=total_ms= 是**累计**
（这个小时为此付了多少代价）、=max_ms= 是**最坏单次**（最影响体感的那一次）。亚秒级卡顿的
问题形态就是这三问，不需要时间戳与栈 —— 定位要靠同时段的 =hourly_functions= /
=hourly_stacks= 采样。因此本表**不记时间戳、不记栈、不记命令**。

**命令内的停转不进本表**：命令**内部**的停转由 =commands= 的 =duration_ms= 精确记录
（≥ =el-chronos-slow-command-threshold-ms= 默认 200ms 时另进 =slow_events(kind='command')=）。
排除机制**不靠任何判据**，而是采集侧在命令结算（=--finish=）后把心跳基线重置到当前时刻，
命令执行时间**根本不进入** =gap=。推论（必须记住）：=hourly_drift= 的时长与 =commands= 的耗时
**不可相加、也不该相加** —— 两者是不相交的集合（「命令间隙的停转」vs「命令总耗时」）。
任何「总卡顿 = 慢命令 + block + drift」的求和式都是错的。

**=total_ms= / =max_ms= 是高估值，不是精确值**：单次时长以「发现时刻距上次心跳基线的间隔」计时，
每次最多多算一个心跳间隔（=el-chronos-heartbeat-seconds=，默认 250ms）。所以
「=max_ms= 减掉至多 250ms」才是真实停转的下界；反过来，真实 ≥250ms 的停转才可能被记
（检出下界是相位相关的 250–500ms，不是精确的 500ms）。

**不写外键**（与 v2 四张及 =hourly_functions= / =hourly_stacks= 一致）：不与 purge 的删除顺序、
级联删除、=foreign_keys=ON= 三者耦合。代价是孤儿行只能靠 purge 顺序约定 + 写入前的会话存在性
校验消灭（见下节与「purge 的 12 表删除顺序」）。

**保留策略**：**永久保留**（小时聚合，仅 =M-x el-chronos-purge= 清理），
=el-chronos-store--prune= **不碰它**（自动 retention 永远只删 =commands= / =slow_events= 两张明细表）。

** hourly_resources（进程资源的小时聚合，v4）

| 字段 | 类型 | 说明 |
|---|---|---|
| =hour_ts= | INTEGER NOT NULL | 整点（epoch ms） |
| =session_id= | INTEGER NOT NULL | 会话 id |
| =cpu_ms= | REAL NOT NULL DEFAULT 0 | 本小时**采样窗口**累计的进程 CPU 时间（毫秒），upsert **累加** |
| =wall_ms= | REAL NOT NULL DEFAULT 0 | 同批累计的墙钟时间（毫秒），upsert **累加** |
| =rss_kb_max= | INTEGER | 进程常驻集大小**峰值**（**KB**），upsert 取标量 =MAX= |
| =rss_kb_sum= | INTEGER | 进程常驻集大小**累加和**（KB），upsert 条件累加 |
| =threads_max= | INTEGER | 进程线程数**峰值**，upsert 取标量 =MAX= |
| =load1_sum= | REAL | 系统负载 1 分钟值的累加和 |
| =load5_sum= | REAL | 系统负载 5 分钟值的累加和 |
| =load15_sum= | REAL | 系统负载 15 分钟值的累加和 |
| =load_n= | INTEGER NOT NULL DEFAULT 0 | **负载样本条数**（每次采样三值同时到达，一条样本记 1） |

主键：=(hour_ts, session_id)=（每会话每小时一行）。**不写外键**（同 v2 / v3 各表）。

**语义限定（不读这一段必然误读）**：

- **=cpu_ms= / =wall_ms= 是增量累加量，不是瞬时值**：它们是本小时内各采样窗口的**和**。
  进程 CPU 占用率 = =SUM(cpu_ms) / SUM(wall_ms)=（见下方「查询 4」）。**不能**先按桶算
  =cpu_ms / wall_ms= 再 =avg()= —— 各桶的分母（窗口总时长）不同，直接平均会给出错的数。
- **=rss_kb_max= 与 =rss_kb_sum= 并存不是冗余**：=max= 抓峰值（内存回归最先表现在峰值上），
  =sum= 抓体重（峰值相同的两小时，平均占用可能差一倍）。均值 = =rss_kb_sum / load_n=。
- **=load*_sum= 存和而非均值**：写库时不知道本小时最终会有多少样本，先算均值会因样本陆续到达而
  失真。均值 = =loadN_sum / load_n=，**分母是 =load_n= 而不是窗口总数**。
- **可空列的 NULL 语义是「从未观测到该指标」**（平台不支持 / 采样关闭 / TRAMP 下取不到），
  0 则是「观测到了，值为 0」。写层用 =COALESCE= / 条件累加保证「=nil= 不覆盖既有非 NULL 值」
  （与 =hourly_gc.heap_bytes= 同一类陷阱）。
- **=cpu_ms= / =wall_ms= 是上一句的唯一例外（TD-28）**：这两列是 =NOT NULL DEFAULT 0=，
  =process-attributes= 的 =time= 字段缺失（平台不支持 / 读失败）时采集侧传 nil，落库被列约束
  兜成 **0**，于是 =cpu_pct = 0=。这个 0 有**两种互斥含义**：①本窗口**没采到** CPU 时间；
  ②进程真的空闲 —— 库里编码相同，=COALESCE= 保上次值对这两列**不生效**，0 还会参与
  =cpu_ms = cpu_ms + excluded.cpu_ms= 的累加把均值往小拉。读法见
  =el-chronos-collect--collect-resources= 与 =el-chronos-store-record-resources= 的 docstring：
  **=cpu_pct = 0= 应先读作「未采集到 CPU 时间」**，判空闲要拿同行的 =samples= 与 RSS 旁证。
  彻底区分需 schema **v5**（两列改可空，或加 =cpu_n= 采样计数），见技术债 TD-28。
- **=load_n = 0 时均值是 NULL 而不是 0**：报告与 Web 渲染 =-=（I11：不做「0 负载」的假象）。
  已知后果：负载采集全部失败的时段，RSS 均值同样为 NULL（刻意的诚实降级，独立 =rss_n= 列
  见技术债）。
- **本表不含任何用户内容**（不涉 I7）：只查 =(emacs-pid)= 自己的 =process-attributes=，
  不遍历全系统进程、不读命令行、不读 buffer。**明确不采系统内存**（=memory-info= 是整机内存，
  且 remote =default-directory= 下查的是远端主机）。

**保留策略**：**永久保留**（小时聚合，仅 =M-x el-chronos-purge= 清理），
=el-chronos-store--prune= **不碰它**（自动 retention 永远只删 =commands= / =slow_events= 两张明细表）。

** 六张新表均不写外键（与 hourly_functions / hourly_stacks 一致）

既有 DDL 里**只有 =commands.session_id REFERENCES sessions(id)=** 一处外键。新六张表刻意不写：

- 写外键会把「purge 的删除顺序」「级联删除」「=foreign_keys=ON=」三者耦合起来——任何一处顺序调整
  都可能变成运行期约束错误；
- 代价是孤儿行只能靠 =purge= 的删除顺序约定消灭，这正是「purge 的 12 表删除顺序」要把顺序钉死、
  并为它写用例的原因；
- 因此写入侧要自己守门：flush 写 =hourly_gc= / =hourly_health= / =startup_phases= / =hourly_drift= /
  =hourly_resources= 前先校验会话行存在（=--session-known-p=），不存在则跳过这几张表并每进程只告警一次。

* 4 个典型查询

** 查询 1：热点函数 TOP（最近 7 天，按 self 时间）

#+BEGIN_SRC sql
SELECT function,
       package,
       SUM(self_ms)                                    AS self_ms,
       SUM(total_ms)                                   AS total_ms,
       SUM(samples)                                    AS samples
FROM hourly_functions
WHERE hour_ts >= :since_ms
GROUP BY function, package
ORDER BY self_ms DESC
LIMIT 30;
#+END_SRC

** 查询 2：慢命令 TOP（最近 7 天，按最大单次；P95 见「百分位（P95）说明」）

#+BEGIN_SRC sql
SELECT name,
       COUNT(*)                                        AS calls,
       SUM(duration_ms)                                AS total_ms,
       MAX(duration_ms)                                AS max_ms,
       SUM(CASE WHEN outcome = 'aborted' THEN 1 ELSE 0 END) AS aborted
FROM commands
WHERE ts >= :since_ms
GROUP BY name
HAVING calls >= 3
ORDER BY max_ms DESC
LIMIT 30;
#+END_SRC

** 查询 3：包归因占比（最近 7 天，按 self 时间）

#+BEGIN_SRC sql
SELECT COALESCE(package, 'unknown')                    AS package,
       SUM(self_ms)                                    AS self_ms,
       ROUND(100.0 * SUM(self_ms)
             / (SELECT SUM(self_ms) FROM hourly_functions WHERE hour_ts >= :since_ms), 1) AS pct
FROM hourly_functions
WHERE hour_ts >= :since_ms
GROUP BY package
ORDER BY self_ms DESC;
#+END_SRC

** 查询 4：进程 CPU 占用率与内存峰值（最近 7 天，按小时桶）

#+BEGIN_SRC sql
SELECT hour_ts,
       SUM(cpu_ms)                                   AS cpu_ms,
       SUM(wall_ms)                                  AS wall_ms,
       100.0 * SUM(cpu_ms) / SUM(wall_ms)            AS cpu_pct,
       MAX(rss_kb_max)                               AS rss_kb_max,
       SUM(rss_kb_sum) / NULLIF(SUM(load_n), 0)      AS rss_kb_avg,
       MAX(threads_max)                              AS threads_max,
       SUM(load1_sum) / NULLIF(SUM(load_n), 0)       AS load1_avg
FROM hourly_resources
WHERE hour_ts >= :since_ms
GROUP BY hour_ts
ORDER BY hour_ts;
#+END_SRC

要点（**口径坑，写错不报错只让数字错**）：

- **CPU% 必须先各自求和再相除**（=SUM(cpu_ms) / SUM(wall_ms)=），**不能** =AVG(cpu_ms / wall_ms)=
  或 =AVG(cpu_pct)= —— 各小时桶 / 各会话片段的窗口总时长不同，先算比率的平均是错的。
- **RSS 与负载的均值分母是 =SUM(load_n)=**（成功取到 =load-average= 的窗口数），不是行数、
  也不是窗口总数；用 =NULLIF(SUM(load_n), 0)= 让「一个负载样本都没有」时返回 **NULL 而非 0**
  （I11：不做「0 负载」的假象）。
- 跨会话（同小时多会话行）时上面两处 =SUM= 都会自动按会话合并，无需额外分组。

* 保留策略

| 表 | 保留 | 说明 |
|---|---|---|
| =sessions= | 随明细一起（=started_at= 同口径） | 每启动一次一行；自动 retention 不动它，=el-chronos-purge= 按 =started_at= 删 |
| =commands= | =el-chronos-retention-days=（默认 30 天） | 每命令一行的明细，超期删除（=--prune=） |
| =slow_events= | 同 =commands= | 慢事件与阻塞事件明细，超期删除 |

| =hourly_stacks= | **永久** | top-N 淘汰（默认 200/小时/会话），行数 ≤ 24 × 200 × 会话数/天 |
| =hourly_gc= | **永久**（仅 purge） | 每会话每小时 ≤ 1 行；与既有 =hourly_*= 同量级 |
| =hourly_health= | **永久**（仅 purge） | 每会话每小时 ≤ 6 行（6 个固定键）；与既有 =hourly_*= 同量级 |
| =hourly_drift= | **永久**（仅 purge） | 每会话每小时 ≤ 1 行；只在命令外 500–2000ms 停转发生时写入，主键去重 upsert。与 =commands= 的时长**不可相加** |
| =hourly_resources= | **永久**（仅 purge） | 每会话每小时 ≤ 1 行；v4 新增。只在 10 秒采样 tick 上写入，主键去重 upsert；行数上界与 =hourly_gc= 同量级 |
| =startup_phases= | 随 =sessions= 由 purge 清理 | **每会话 ≤ top-N + 3 行**（默认 ≤ 53 行，=first-idle= 记录时 ≤ 54）—— 比 =sessions= 的 1 行/会话高两个量级，长期频繁重启的机器上会明显增长，是本项目最值得留意的一张表 |

- 自动 retention（=el-chronos-store--prune=）**只作用于 =commands= / =slow_events=**，不得动
  七张 =hourly_*= 聚合表（=hourly_functions= / =hourly_usage= / =hourly_stacks= / =hourly_gc= /
  =hourly_health= / =hourly_drift= / =hourly_resources=；趋势与跨年对比依赖它们），也不得动两张
  会话级表（=startup_phases= / =session_meta=）。
- 七张 =hourly_*= 与两张会话级表的唯一清理途径都是用户手动 =M-x el-chronos-purge=（按日期或全部）。
- 清理在低优先级 timer 中执行，避免占用交互时段。

* 百分位（P95）说明：当前是近似

SQLite 没有百分位聚合函数，当前实现**不用**「=ORDER BY … LIMIT/OFFSET= 排序取位」逐条扫描，
而是走两条近似路径：

1. **排行按 max / avg 展示**（=el-chronos-analysis-slow-commands= 返回 =:max-ms= / =:avg-ms=），
   不声称是 P95；
2. 需要长尾刻画时看 =slow_events= 的阻塞与超阈值事件分布，以及趋势桶的计数。

精度风险见 TD-7：长尾分布下，「排序取位」与「分桶直方图」两种算法在样本量大且分布偏斜时可能
偏差 >5%。**待实测**（见文末待补）；偏差超阈值时改为 =commands= 按 =duration_ms= 预分桶的直方图表，
而不是在查询时排序取位。

* purge 的 12 表删除顺序（钉死，不许改写）

=el-chronos-store--purge-targets= 是 =(表名 . 删除策略)= 的列表，**顺序不可改**。
两种策略：=ts= / =hour-ts= 表示表里有时间列、按列删（=ts < ?= / =hour_ts < ?=）；
=stale-session-rows= / =stale-session= 表示表里没有（可信的）时间列、按**所属会话子查询**删
（判据见下）。

| 步骤 | 表 | 删除条件 | 为什么必须在这一步 |
|---|---|---|---|
| 1 | =commands= | =ts < ?= | **唯一带外键的表**（=session_id REFERENCES sessions(id)=，打开库即 =foreign_keys=ON=）→ 必须最先，否则后面删 =sessions= 会撞约束、整个 purge 回滚 |
| 2 | =slow_events= | =ts < ?= | 无外键，紧跟明细表 |
| 3 | =startup_phases= | =session_id IN (SELECT id FROM sessions WHERE <stale-session-sql>)= | **必须在 =sessions= 之前**：删完 =sessions= 后子查询恒空 → 这行数据永远删不掉，留下孤儿 |
| 4 | =session_meta= | 同上 | 同上（且是**隐私表**，更不允许残留） |
| 5 | =hourly_functions= | =hour_ts < ?= | 聚合表，按时间列删 |
| 6 | =hourly_usage= | =hour_ts < ?= | 同上 |
| 7 | =hourly_stacks= | =hour_ts < ?= | 同上 |
| 8 | =hourly_gc= | =hour_ts < ?= | 同上（v2 新表） |
| 9 | =hourly_health= | =hour_ts < ?= | 同上（v2 新表） |
| 10 | =hourly_drift= | =hour_ts < ?= | 同上（v3 新表，带 =hour_ts= 时间列 → 按列删）。位置在 =hourly_health= 之后、=sessions= 之前：与其余五张聚合表同一个顺序理由（有 =hour_ts= 列、按列删、必须早于 =sessions=） |
| 11 | =hourly_resources= | =hour_ts < ?= | 同上（v4 新表，带 =hour_ts= 时间列 → 按列删）。紧跟 =hourly_drift=，与其余六张聚合表同一个顺序理由 |
| 12 | =sessions= | =started_at < ?= 且无存活子行 | **最后**：它是第 1 步外键的父表、第 3–4 步子查询的源表 |

**两条互不相同的顺序理由，不要混为一谈**：

1. **外键只约束 =commands=** → 第 1 步必须最早。既有 DDL 里仅 =commands.session_id REFERENCES
   sessions(id)=；=hourly_functions= / =hourly_usage= / =hourly_stacks= 与 v2 / v3 / v4 六张新表**都没有外键**。
2. **=startup_phases= / =session_meta= 必须在 =sessions= 之前，理由不是外键而是子查询** →
   它们的删除条件依赖 =SELECT id FROM sessions ...=。若先删 =sessions=，子查询在删完之后恒为空，
   两表的行**永远不会被删且不报错**，静默成为孤儿，直接破坏 purge「删掉这段历史」的语义。
   这是最容易漏的一条。

**过期会话判据（三张会话相关表共用）**：=el-chronos-store--stale-session-sql= 为
=started_at < ? AND id NOT IN (SELECT DISTINCT session_id FROM commands WHERE ts >= ?)=，
两个占位符都绑同一个 =BEFORE=。排除「仍有 =ts >= BEFORE= 的 commands 行」的会话是必需的：
=commands= 按 =ts= 删、=sessions= 按 =started_at= 删，口径不同；一个「很久以前启动、今天还在跑」
的会话满足 =started_at < BEFORE=，直接删它会撞外键让**整个 purge 事务回滚**（一条都没删掉，
用户只看到一句限流告警）。宁可保留这个会话（它的过期明细照样按 =ts= 删掉），也不能让整批失败——
=purge= 是隐私清理手段，「以为删了其实没删」比「少删几个会话」严重得多。

**其它约定**：

- =BEFORE= 为 nil（清空全部）时所有表走无条件 =DELETE FROM <table>=，子查询不参与，顺序此时
  无关紧要；但仍照上表执行，保持**单一代码路径**（一个顺序，两种 =BEFORE= 都走）。
- 整个 purge 在单事务内（=BEGIN= / =COMMIT= / 失败 =ROLLBACK=），12 条 DELETE 同一事务。
- purge 结束后重建当前会话行（否则后续写入撞外键）；重建时把该行的 =startup_ms= 显式置 NULL
  —— =--ensure-session= 会用 =before-init-time= → =after-init-time= 写「本进程的启动耗时」，
  而此刻 =started_at = now=，两者语义矛盾（=started_at= 说「刚启动」、=startup_ms= 说「几小时前启动」）。
- =--prune= **不加**任何新表：它只删 =commands= / =slow_events= 两张明细表。

* 迁移 v1 → v2（显式事务 + .bak 回滚）

v1（6 表）→ v2（10 表）的迁移**一条 =ALTER TABLE ADD COLUMN= 都没有**，全部是四条
=CREATE TABLE IF NOT EXISTS=。理由：

- =ALTER TABLE … ADD COLUMN= **不幂等**：第二次执行报 =duplicate column name=。而迁移在失败重试、
  =.bak= 恢复后重开、崩溃后重启时都会重跑，只要有一条 ALTER 就不可能安全。
- 四条 =CREATE TABLE IF NOT EXISTS= 天然幂等 → 迁移脚本可以**无条件重跑**，失败恢复路径不必
  记录「做到第几步」。
- 附带解耦：新维度不挤进既有 6 表，既有表的行宽与索引一字节不变。

**实现要点（=el-chronos-store--migrate=）**：

1. 先 =PRAGMA wal_checkpoint(TRUNCATE)=（WAL 未 checkpoint 时主文件不含最新数据）；
2. 复制 =.bak= —— **必须在 =BEGIN= 之前**，备份要反映迁移前的完整状态；
3. =BEGIN= → =sqlite-execute-batch= 跑 =--sql-migrate-v2= → =PRAGMA user_version=2= → =COMMIT=。
   **必须显式包事务**：=sqlite-execute-batch= 不自带事务（逐条隐式提交），不开事务时最坏状态是
   「4 张表只建成 3 张、=user_version= 仍是 1」—— 库对外是半成品：分析层因缺表静默降级（返回空结果，
   看似「无数据」而实际是「迁移没做完」），外部 =sqlite3= 读者看到残缺 schema。
4. 失败分支：先 =ROLLBACK=（**必须在 =.bak= 覆盖之前**，否则覆盖时句柄仍持有未回滚事务）→
   关句柄 → =.bak= 覆盖回原文件 → 删 =-wal= / =-shm= → =display-warning= → 返回 nil。
5. 版本分支用 =(when (= version 1) …)= 而不是 =(< version 2)=：进入时的 =version= 变量已按上一级推进
   （0 号库走 =--ensure-schema= 后同步为当前常量），再跑一遍 v2 脚本虽幂等但会让失败恢复路径难以推理。

**关键陷阱（改这里之前必读）**：=el-chronos-store--ensure-schema= 建完表就**无条件**把
=user_version= 置为当前常量。所以 =--schema-ddl= **必须始终是全量 DDL** —— 若只把
=--schema-version= 改成 3 而 DDL 还是旧的 10 表，版本 0 的新库会只建 10 表却被标记为 v3，
之后 =--migrate= 不会再跑（版本相等），=hourly_drift= 永远不存在，所有 drift 写入静默失败。

* 迁移 v2 → v3（新增 =hourly_drift=，迁移链按版本变量逐级推进）

v2（10 表）→ v3（11 表）与 v1 → v2 同款：**一条 =ALTER TABLE= 都没有**，只有一条
=CREATE TABLE IF NOT EXISTS hourly_drift=。增量脚本是常量 =--sql-migrate-v3=，
与 =--schema-ddl= 里的 =--ddl-hourly-drift= **共用同一个字面量**（两份必然漂移，
而漂移的表现是「新库对、旧库缺表」）。

**迁移链的陷阱（本次修掉的硬缺陷，必须在改 =--migrate= 之前读完）**：

S1 及之前的 =--migrate= 是两个**互斥**分支 —— =(when (< from-version 1) …ensure-schema…)=
+ =(when (= from-version 1) …v2 脚本、版本置 2…)=。若本次只追加一个
=(when (= from-version 2) …)=，那么 **=from-version = 1= 的库**（S1 之前建的库，用户升级过一版
但没到 v3）会：走 v2 分支把版本推到 2 → **没有任何分支继续推进 v3** → =--migrate= 返回 t、
=--open-db= 返回可用句柄，但库里**没有 =hourly_drift= 表** → 本次会话所有 drift 写入撞
=no such table= → flush 失败 → 限流告警 + 丢本批 → 下次启动才补上 v3。这是**静默降级型缺陷**
（用户看不到错误，只看到 drift 数据缺一段），因此本次一并修掉。

**定案写法：局部 =version= 变量逐级推进**（=el-chronos-store--migrate= 内）：

#+BEGIN_SRC elisp
(let ((version from-version))
  (when (< version 1)
    (el-chronos-store--ensure-schema db)          ; 建全当时的最新表（现为 12 表）并置 user_version
    (setq version el-chronos-store--schema-version))  ; ← 必须同步为 3，不是 1
  (when (= version 1) …v2 脚本… (sqlite-pragma db "user_version=2") (setq version 2))
  (when (= version 2) …v3 脚本… (sqlite-pragma db "user_version=3") (setq version 3))
  (sqlite-pragma db (format "user_version=%d" version)))
#+END_SRC

三条必须满足的语义（各有守门用例）：

| 起始版本 | 必须发生的事 | 最终状态 |
|---|---|---|
| **0（新库）** | 只走 =--ensure-schema=（建全 11 表 + 版本置当前常量），**不重跑** v2 / v3 脚本 | 11 表、=user_version=3= |
| **1（S1 之前的老库）** | v2 脚本 → 版本 2 → **继续** v3 脚本 → 版本 3（**一次打开就到位**） | 11 表（含 =hourly_drift=）、=user_version=3= |
| **2（S1 的库）** | 只跑 v3 脚本 | 11 表、=user_version=3= |

（本表是 **v3 时代**的守门条件快照；v4 加入后同一组起始版本演化为「12 表 / =user_version=4=」，
完整对照表见下一节「迁移 v3 → v4」。）

**`--ensure-schema=` 的交互是本方案唯一的陷阱**：它建完表后**无条件**写
=user_version = --schema-version=（=3=），所以那次调用返回后库里已是最新，而局部 =version=
还停在原值。三种结局只有一种可接受：

- 留在 **0** → 末尾 pragma 把已经是最新的库标成**版本 0**，下次打开又走一遍迁移
  （幂等但版本号长期失真）—— **禁止**；
- 置成 **1** → 版本号正确，代价是 v2 / v3 脚本各多跑一遍（=CREATE TABLE IF NOT EXISTS=
  幂等不报错，但「刚建全表又迁移两遍」让失败恢复路径难以推理）—— 可行但不推荐；
- 置成 **=--schema-version=（3，采用）** → 后续分支自然都不触发，末尾 pragma 写 3。

其余边界沿用 v1 → v2 的四条：=.bak= 复制在 =BEGIN= **之前**、=ROLLBACK= 在 =.bak= 覆盖**之前**、
每步各自 =BEGIN= / =COMMIT=（步骤内只把版本推进到**本步目标版本**）、末尾统一写一次最终版本。
将来追加 v4 时，本步仍只把版本置为 3，不要「顺手」改成当前常量。

* 迁移 v3 → v4（新增 =hourly_resources=）

v3（11 表）→ v4（12 表）与前面两步**完全同款**：一条 =ALTER TABLE= 都没有，只有一条
=CREATE TABLE IF NOT EXISTS hourly_resources=。增量脚本是常量 =--sql-migrate-v4=，
与 =--schema-ddl= 里的 =--ddl-hourly-resources= **共用同一个字面量**（两份必然漂移，
而漂移的表现是「新库对、旧库缺表」）。

四条实现要点（与前两步一套，逐条都不可省）：

1. **只 =CREATE TABLE IF NOT EXISTS=，不改既有列**：=ALTER TABLE … ADD COLUMN= 不幂等
   （第二次执行报 =duplicate column name=），而迁移在失败重试 / =.bak= 恢复后重开 / 崩溃重启时
   都会重跑 —— 只要有一条 ALTER 就不可能安全。
2. **=PRAGMA user_version=4= 在 =COMMIT= 之前**：显式包事务（=BEGIN= → =sqlite-execute-batch= →
   pragma → =COMMIT=）。不开事务的最坏状态是「表建好了、=user_version= 还是 3」，
   下次打开会重跑一遍（幂等无害）；反过来「版本写 4 但表没建」才是灾难（=--migrate= 不再跑，
   表永远不存在，所有资源写入静默失败）。
3. **=.bak= 回滚**：迁移前 =wal_checkpoint(TRUNCATE)= → 复制 =.bak=（**必须在 =BEGIN= 之前**）；
   失败分支 =ROLLBACK=（**必须在 =.bak= 覆盖之前**）→ 关句柄 → =.bak= 覆盖回原文件 →
   删 =-wal= / =-shm= → =display-warning= → 返回 nil、本轮禁用采集。
4. **逐级推进，老库一次到位**：=--migrate= 用局部 =version= 变量逐级 =when=，
   因此 **v0 / v1 / v2 老库在一次打开里连续走完 v2 / v3 / v4 三步**，最终 12 表齐备、
   =user_version=4=。不会出现「推到 v3 就停住」的半迁移（那是 v2 → v3 这轮修掉的硬缺陷，
   见上一节的「迁移链的陷阱」）。

| 起始版本 | 必须发生的事 | 最终状态 |
|---|---|---|
| **0（新库）** | 只走 =--ensure-schema=（建全 12 表 + 版本置当前常量），**不重跑** v2 / v3 / v4 脚本 | 12 表、=user_version=4= |
| **1（S1 之前的老库）** | v2 脚本 → 版本 2 → v3 脚本 → 版本 3 → **继续** v4 脚本 → 版本 4 | 12 表、=user_version=4= |
| **2（v2 的库）** | v3 脚本 → 版本 3 → v4 脚本 → 版本 4 | 12 表、=user_version=4= |
| **3（v3 的库）** | 只跑 v4 脚本 | 12 表（含 =hourly_resources=）、=user_version=4= |

守门用例：=test/el-chronos-store-test.el= 的 v0→v4 / v1→v4 / v2→v4 / v3→v4 四条迁移用例
（每条都断言「12 表齐备、=hourly_resources= 为空、更早的脚本不重跑」），
外加 =.bak= 回滚与 =--ensure-schema= 后版本同步两条边界。

* 手动清理与迁移回滚

- =el-chronos-purge (&optional before)=：删除指定日期前的**全部**数据（含七张 =hourly_*= 与两张
  会话级表，共 12 张表，顺序见上一节）。不给 =before= 时按 =el-chronos-retention-days= 计算；
  返回按删除顺序排列的 =((表名 . 删除行数) ...)=。用于用户主动清空历史，与自动 retention 区分。
- 迁移流程概览：读 =PRAGMA user_version= → 若低于代码期望版本，先复制 DB 为 =.bak= →
  按版本变量逐级推进执行迁移 SQL（v1 → v2、v2 → v3、v3 → v4，各步显式包事务）→ 全部成功则写新
  =user_version=；任一步失败则用 =.bak= 覆盖回滚 + =display-warning=，本轮禁用采集。
  细节见「迁移 v1 → v2」/「迁移 v2 → v3」/「迁移 v3 → v4」三节。
- 彻底重置：关闭 Emacs 后删除 =chronos.sqlite=（连同 =-wal= / =-shm=）即可，下次启动重建空库
  （=user_version= 4、12 表 + 3 索引）。
