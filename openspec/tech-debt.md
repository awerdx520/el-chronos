# 技术债

记录已知但当前不解决的技术风险与待实测项。计划阶段识别、实现阶段认领、验证阶段关闭。

| 编号 | 描述 | 影响 | 计划 |
|---|---|---|---|
| TD-1 | `symbol-file` 在 native-comp 下可能返回 `.eln`，归因兜底方案（`comp-el-to-eln-filename` 反查）未实测 | 归因可能指向编译产物而非源码，包/模块归属错判为 `unknown` | **已关闭（2026-10-24）**。实测（Emacs 31.1）：显式加载 `.eln` 后 `symbol-file` 确实返回 `…/eln-cache/<版本>-<编译哈希>/<库名>-<8位hex>-<8位hex>.eln`（`load-history` 记录 eln 路径），此前一律归 `unknown`。方案 A 落地（`el-chronos-attrib--classify-eln`）：① `subr--trampoline-*.eln` 与系统 `native-lisp/<版本>-<哈希>/` 目录直接判 `built-in`（零 IO，该目录只放内置库 AOT 产物）；② 用户 eln-cache 从文件名剪掉末尾 1–2 段十六进制哈希得库名，`locate-library` 反查源码路径后沿用原有前缀规则分类，结果按 eln 路径缓存（同一 eln 只反查一次）；③ 反查失败降级 `unknown`，绝不猜包名（宁缺勿错）。未采用方案 B（`comp-el-to-eln-filename` 需遍历候选库反查，代价高）。实测真实 eln-cache 844 个 `.eln`：815 个反查成功（96.6%，其中 814 落 straight build），加 trampoline 判 `built-in` 后**仅 9 个 `unknown`（1.1%）**，共归因到 162 个不同包。剩余边界：已删除包的残留 eln、snippet 临时文件（`.yas-setup-*`）仍为 `unknown`（按设计） |
| TD-2 | 非命令型阻塞（timer / 进程过滤器 / redisplay）的捕获覆盖率未实测 | 心跳检测只能发现「主线程停转」，长耗时的 timer 回调与进程过滤器可能被误记为普通阻塞且无命令上下文 | **已关闭（2026-10-24 实测）**：命令外停转由 1s 心跳覆盖，实测 ≥2s 的计算型停转 **5/5 捕获**（命令内 3s 忙等、timer 回调 2.5/3.0s、进程过滤器 3.0s、`font-lock-fontify-buffer` 10 万行 2.4s；另 `garbage-collect` 92ms 与 1.5s 停转按预期漏记）。精度：**记录值 = 真实停转 + 偏移**，偏移 ∈ [0, 1 心跳间隔]，恒高估（B/G 两组预测-实测对齐，误差 ≤0.2ms；1.6s 停转在贴近心跳处开始被记成 2.58s，高估 61%）。检出下界：最好相位 ~0.95s，最差相位需真实 >2s。命令内停转 ≥2s 会**双记** `kind='command'`（精确）+ `kind='block'`（高估 ≤1s）。`block` 事件的 `command` / `stack_json` 恒 NULL，定位靠同时段采样。残余缺口（<2s 停转不可见、等待型调用零覆盖、GUI redisplay 未实测）转 TD-11。数据与方法见 `docs/architecture.org`「实测结论 10」 |
| TD-3 | 10ms 采样开销未实测，超 0.5% CPU 需退到 20/50ms | 常驻采样本身可能成为开销源，违背「低开销观测器」定位 | **已关闭（2026-10-24 实测）**：结论「10ms 默认开销远低于 0.5%，保持 10ms」，不改默认值。方法（针对上次 float-time 墙钟 ±9% 抖动重做）：主指标 `get-internal-run-time`（进程 CPU 时间）+ **相位级 ABBA**（[关,开,开,关]/[开,关,关,开]，profiler 在整段相位内连续常驻、只在相位边界起停，每相位 50 个 ~7.5ms 微块、栈深 20 的整数无分配负载），每档 7 轮取中位数，控制组「间隔 10s」（几乎不采样）给出噪声地板。实测（每轮 on/off 各 ~1.5s CPU）：**5ms −0.59% / 10ms +0.98% / 20ms −1.11% / 控制组 −0.66%** —— 全部落在噪声地板 ±0.7–1.1% 之内、且与采样率无单调关系，说明 10ms 量级的效应**低于本机测量分辨率**（不是「测出 0.98%」）。决定性锚点在更高采样率：**1ms 间隔实测 +0.46%**，采样率约 10×（2887 样本/轮，与理论值吻合），单样本成本 C ≈ 1µs 量级；按实测采样率（10ms 档 145–285 样本/0.75s ≈ 200–370 样本/s）外推 10ms 开销 ≈ **0.02–0.2%**，上限仍低于 0.5%，故保持默认 10ms。采集模式（`el-chronos-mode` 开/关，含采样 + 1s 心跳 + 存储缓冲）：10ms 中位 +1.98%（各轮 −2.31%…+7.37%，噪声主导）、20ms 中位 +0.15%，同样无法与噪声区分。**方法论教训（重要）**：`profiler-cpu-start` 会把采样定时器重置为「间隔后首次触发」，若每个微块都 start/stop 一次，则当间隔 > 微块时长时**一个样本都采不到**（10/20/100ms 档每块 distinct 栈 = 0，测到的只是 start/stop 的 0.04ms 成本）——必须相位级常驻。另：`profiler-cpu-log` 是「栈→样本数」hash table，`hash-table-count` 是 distinct 栈数而非样本数，样本数须 `maphash` 求和。**环境噪声**：WSL2 下相同工作负载的相位 CPU 时间漂 24%（float 分配型负载 40%），这是分辨率上限，无法靠加轮次完全消除 |
| TD-4 | Makefile 在无 `.el` 仓库初期的目标空跑行为未在 CI 验证 | 空跑分支只在本地手工验证过；CI 环境差异（`find` 行为、`make` 版本）可能导致误失败 | T1 已本地验证；Phase 3 接入 CI 时补一条「空仓库 `make full-check` 通过」的门禁用例 |
| TD-5 | ETAF 页面在大量行 / 多图表重绘下的性能未实测（`etaf-ui-table` 分页 20 行 + 3 张 SVG 图） | 数据量大时页面可能卡顿，反而成为「观测器自己慢」的新问题 | **已关闭（2026-10-24）**：dashboard 模块已删除，ETAF 重绘性能不再有测量对象；如需评估 Web 渲染性能，另立技术债（见 ADR-0003） |
| TD-6 | Web 无鉴权，且 loopback 不构成本机访问控制（WSL2 mirrored 下 Windows 侧进程可达） | 本机其他进程或多用户环境可读取全部采集数据 | 已在 I8 / 隐私边界显式声明为「本机自用只读视图」；Phase 3 评估加最小 token 校验，或仅在显式 `el-chronos-web-start` 期间监听 |
| TD-7 | P95 用 `ORDER BY duration_ms DESC LIMIT/OFFSET` 近似的精度未评估 | 长尾分布下分页近似可能明显偏离真实百分位，误导优化优先级 | T6/T7 完成后用 fixture 数据对比「排序取位」与「分桶直方图」两种算法误差；偏差 >5% 改用直方图表 |
| TD-8 | 命令 error 检测依赖 `command-error-default-function` 的 advice：Emacs 30+ 默认 `command-error-function` 是 `help-command-error-confusable-suggestions`（内部仍调默认实现，实测 2026-10-24 Emacs 31.1 可用）；若用户把它换成**不委托**给默认实现的函数，则 error 无法识别 | 该用户的错误类命令会被记为 `ok`（若未走 `post-command-hook` 则记 `aborted`），`outcome='error'` 统计偏低 | T5 已用 advice 方案落地并在可用路径实测；后续评估补兜底（如检测到自定义 `command-error-function` 时告警） |
| TD-9 | Emacs 31 起 `pre-command-hook` / `post-command-hook` 是 auto-buffer-local（`local-variable-if-set-p` 为 t）：`add-hook` 无 LOCAL 时只改**默认值**，已有局部绑定的 buffer（实测 `*scratch*` 被 eldoc 留了局部值）会遮蔽全局值 | 那些 buffer 里的命令不会被计时（漏采），数据完整性下降 | **已修复（2026-10-24）**：改为「全局默认值 + 每个 buffer 局部补挂」双路——`el-chronos-collect-start` 仍装全局 `add-hook`，新增 `el-chronos-collect--ensure-buffer-hooks` 遍历 `buffer-list` 逐个补挂局部值并登记到 `el-chronos-collect--hooked-buffers`（weak key），`buffer-list-update-hook` 负责新 buffer 增量补挂；`el-chronos-collect-stop` 先摘 `buffer-list-update-hook`，再由 `el-chronos-collect--clean-buffer-hooks` 用 `remove-hook ... LOCAL=t` 摘局部值、对「摘后已回落到默认值」的局部绑定再 `kill-local-variable`（不把遮蔽坑留给用户）、最后 `clrhash` 登记表。验收：被遮蔽 buffer 内命令计时恢复（`emacs -Q --batch` 端到端捕获到 `move-end-of-line` 事件）、连续 3 轮 start/stop 无重复挂、stop 后局部值与登记表零残留 |
| TD-10 | `total_ms` 与内置 `profiler-report` 的 total 列口径不完全相等：本模块按**栈内去重**累加（同一函数在一条栈里出现多次只算一次），内置报告按每帧累加 | 同一份采样数据在两处读数不同，跨工具对比时易被误判为数据错乱或 bug | **文档已注明（2026-10-24）**：`el-chronos-collect.el` 文件头 2b 与计划「注意事项」均写明 samples 为 self 口径（leaf 采样次数）、`total_ms` 为出现时间（栈内去重）；不打算对齐——去重口径才符合「经过该函数的样本数」语义，且避免深递归函数的 total 被重复帧放大 |
| TD-11 | TD-2 实测后确认的阻塞捕获残余缺口：① **<2s 停转**（GC、单次 font-lock 片段、短同步 IO）完全不进 `slow_events`，只能从采样表小时聚合间接看出；② `kind='block'` 的 `duration_ms` 是「真实 + 0…1 心跳间隔」的**系统性高估**（实测 1.6s 被记成 2.58s，+61%）；③ 命令内停转 ≥2s 会同时记 `kind='command'`（精确）与 `kind='block'`（高估），两类求和即重复计数；④ 进程过滤器阻塞时 `context` 里的 mode/project 取的是心跳时刻的当前 buffer，可能与被阻塞的进程无关；⑤ GUI `redisplay` 阻塞未实测（`--batch` 下 `redisplay t` 恒为 0ms） | 用户看到的单次卡顿时长偏高（≤1s），亚秒级卡顿看起来「不存在」，跨口径求和时总时长重复计 | 建议（**均未实施**，按性价比排序）：① 心跳间隔降到 200–250ms，把高估上界压到 0.25s（须先测 5 倍 timer 唤醒的开销，与 TD-3 合并评估）；② 把亚阈值漂移累加进小时聚合（或复用 `slow_events` 加 `kind='drift'`、阈值 500ms），让 1s 级卡顿可见；③ 心跳记 `kind='block'` 时若 `el-chronos-collect--pending-p` 为真则把当前命令名填进 `command` 列，供去重与下钻；④ GUI 侧用真实 frame 复测 redisplay 阻塞（原计划并入 TD-5，TD-5 已随 dashboard 下线关闭，需独立安排）。实测数据与方法见 `docs/architecture.org`「实测结论 10」 |
| TD-12 | **Web 请求处理未纳入自观测抑制**：`el-chronos-web.el` 不绑定 `el-chronos-collect--suppress-block-p`，重查询（如 30 天趋势 + 火焰图）在主线程同步处理期间可能被 1s 心跳判为一条 block 事件并落库 | Web 上的重查询会在 `slow_events(kind='block')` 里留下"观测器自伤"记录，与真实用户卡顿混淆 | 待评估：① 在 `el-chronos-web--dispatch` 外层复用 `el-chronos-report--without-block-events` 同款抑制（绑定 + 抬阈值 + `unwind-protect` 重置基线）；② 或接受现状并在报告/dashboard 侧按 `context` 过滤。**注意**：dashboard 删除后抑制覆盖面只剩 report，本项属既有缺口而非本次引入（2026-10-24 由 T4b 核查发现） |

## 使用约定

- 新发现风险追加 TD-N（编号连续），不删除历史条目——关闭时在「计划」列末标注 `已关闭（YYYY-MM-DD）`。
- 影响面涉及不变量（I1–I11）的条目须同时在 `openspec/decisions.md` 留决策记录。
