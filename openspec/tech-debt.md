# 技术债

记录已知但当前不解决的技术风险与待实测项。计划阶段识别、实现阶段认领、验证阶段关闭。

| TD-1 | `symbol-file` 在 native-comp 下可能返回 `.eln`，归因兜底方案（`comp-el-to-eln-filename` 反查）未实测 | 归因可能指向编译产物而非源码，包/模块归属错判为 `unknown` | **已关闭（2026-10-24）**。实测（Emacs 31.1）：显式加载 `.eln` 后 `symbol-file` 确实返回 `…/eln-cache/<版本>-<编译哈希>/<库名>-<8位hex>-<8位hex>.eln`（`load-history` 记录 eln 路径），此前一律归 `unknown`。方案 A 落地（`el-chronos-attrib--classify-eln`）：① `subr--trampoline-*.eln` 与系统 `native-lisp/<版本>-<哈希>/` 目录直接判 `built-in`（零 IO，该目录只放内置库 AOT 产物）；② 用户 eln-cache 从文件名剪掉末尾 1–2 段十六进制哈希得库名，`locate-library` 反查源码路径后沿用原有前缀规则分类，结果按 eln 路径缓存（同一 eln 只反查一次）；③ 反查失败降级 `unknown`，绝不猜包名（宁缺勿错）。未采用方案 B（`comp-el-to-eln-filename` 需遍历候选库反查，代价高）。实测真实 eln-cache 844 个 `.eln`：815 个反查成功（96.6%，其中 814 落 straight build），加 trampoline 判 `built-in` 后**仅 9 个 `unknown`（1.1%）**，共归因到 162 个不同包。剩余边界：已删除包的残留 eln、snippet 临时文件（`.yas-setup-*`）仍为 `unknown`（按设计） |
| TD-2 | 非命令型阻塞（timer / 进程过滤器 / redisplay）的捕获覆盖率未实测 | 心跳检测只能发现「主线程停转」，长耗时的 timer 回调与进程过滤器可能被误记为普通阻塞且无命令上下文 | **已关闭（2026-10-24 实测）**：命令外停转由 1s 心跳覆盖，实测 ≥2s 的计算型停转 **5/5 捕获**（命令内 3s 忙等、timer 回调 2.5/3.0s、进程过滤器 3.0s、`font-lock-fontify-buffer` 10 万行 2.4s；另 `garbage-collect` 92ms 与 1.5s 停转按预期漏记）。精度：**记录值 = 真实停转 + 偏移**，偏移 ∈ [0, 1 心跳间隔]，恒高估（B/G 两组预测-实测对齐，误差 ≤0.2ms；1.6s 停转在贴近心跳处开始被记成 2.58s，高估 61%）。检出下界：最好相位 ~0.95s，最差相位需真实 >2s。命令内停转 ≥2s 会**双记** `kind='command'`（精确）+ `kind='block'`（高估 ≤1s）。`block` 事件的 `command` / `stack_json` 恒 NULL，定位靠同时段采样。残余缺口（<2s 停转不可见、等待型调用零覆盖、GUI redisplay 未实测）转 TD-11。数据与方法见 `docs/architecture.org`「实测结论 10」 |
| TD-3 | 10ms 采样开销未实测，超 0.5% CPU 需退到 20/50ms | 常驻采样本身可能成为开销源，违背「低开销观测器」定位 | **已关闭（2026-10-24 实测）**：结论「10ms 默认开销远低于 0.5%，保持 10ms」，不改默认值。方法（针对上次 float-time 墙钟 ±9% 抖动重做）：主指标 `get-internal-run-time`（进程 CPU 时间）+ **相位级 ABBA**（[关,开,开,关]/[开,关,关,开]，profiler 在整段相位内连续常驻、只在相位边界起停，每相位 50 个 ~7.5ms 微块、栈深 20 的整数无分配负载），每档 7 轮取中位数，控制组「间隔 10s」（几乎不采样）给出噪声地板。实测（每轮 on/off 各 ~1.5s CPU）：**5ms −0.59% / 10ms +0.98% / 20ms −1.11% / 控制组 −0.66%** —— 全部落在噪声地板 ±0.7–1.1% 之内、且与采样率无单调关系，说明 10ms 量级的效应**低于本机测量分辨率**（不是「测出 0.98%」）。决定性锚点在更高采样率：**1ms 间隔实测 +0.46%**，采样率约 10×（2887 样本/轮，与理论值吻合），单样本成本 C ≈ 1µs 量级；按实测采样率（10ms 档 145–285 样本/0.75s ≈ 200–370 样本/s）外推 10ms 开销 ≈ **0.02–0.2%**，上限仍低于 0.5%，故保持默认 10ms。采集模式（`el-chronos-mode` 开/关，含采样 + 1s 心跳 + 存储缓冲）：10ms 中位 +1.98%（各轮 −2.31%…+7.37%，噪声主导）、20ms 中位 +0.15%，同样无法与噪声区分。**方法论教训（重要）**：`profiler-cpu-start` 会把采样定时器重置为「间隔后首次触发」，若每个微块都 start/stop 一次，则当间隔 > 微块时长时**一个样本都采不到**（10/20/100ms 档每块 distinct 栈 = 0，测到的只是 start/stop 的 0.04ms 成本）——必须相位级常驻。另：`profiler-cpu-log` 是「栈→样本数」hash table，`hash-table-count` 是 distinct 栈数而非样本数，样本数须 `maphash` 求和。**环境噪声**：WSL2 下相同工作负载的相位 CPU 时间漂 24%（float 分配型负载 40%），这是分辨率上限，无法靠加轮次完全消除。**方法论补充（2026-10-25 补记）**：微基准若轮内发生 GC（`emacs -Q --batch` 下单次约 7.7ms）会把 µs/call 抬高一个量级，须计数 `gcs-done` 丢弃污染轮；且 timer 唤醒成本随唤醒率 regime 变化（低唤醒率 87µs / 高唤醒率 24µs），高频锚点不能直接外推到低频——外推方向与本条「按单位工作量外推」相反（本条的采样成本属「每单位工作量」；详见 `docs/architecture.org` 实测结论 13） |

| TD-32 | **GC 归因的 command 维度覆盖率有限（以 `<none>` 为主）**：归因键是 GC 时刻的 `this-command`，而**GC 时刻没有正在执行的命令**时它是 nil → 落哨兵 `"<none>"`。这一档不止「启动期 / batch」，还包含**命令循环等待输入期间**、**idle timer 回调**、**进程过滤器回调**（都不在命令执行中）。**旧稿「此时 `this-command` 是上一条命令」的说法已按实测与 `info` 手册改正**——命令循环只在运行命令前才设置 `this-command`，等待输入期间它是 nil 而非上一条命令 | 本机真实库实测：**45 次归因中 37 次（88.1%）落 `<none>`**，且集中在交互会话（`eca-chat-mode` 21 / `fundamental-mode` 10 / `magit-status-mode` 3），**不是**启动期或 batch——即「按命令归因」在这台机器上只对约 12% 的 GC 有效，命令维度实际只服务「命令执行期 GC」；「这次 GC 是谁触发的」在等待输入期间仍无答案（mode 维度可用且更稳） | **不修（物理边界）**：没有正在执行的命令就没有命令可归因；`major-mode` 虽多数时候有值，但命令维度缺失。若将来要补，需引入**新维度**（按最近结算的命令回溯、或按 timer / 进程过滤器来源分类），不能靠改键表达式得到，属新维度设计。同一结论必须原样出现在 `el-chronos-collect--post-gc` docstring、`el-chronos-report--gc-attrib-caveat`、`docs/architecture.org`「路径 6：GC 与自监控」、`docs/schema.org` 与 `AGENTS.md`「已知边界」，**不得**改回「idle 里是上一条命令」的旧文案 |
| TD-33 | **GC 归因键用 `this-command`，与 `commands.name` 的 `real-this-command` 口径不一致**：`el-chronos-collect--post-gc` 直接取 `this-command`，而命令计时经 `--command-label` 取 `(or (bound-and-true-p real-this-command) this-command)`（`real-this-command` 优先，`simple.el` 原注释：让 `M-x <cmd> RET` 等同于直接运行实际命令）；两处口径不同 | 命令内部 `setq this-command` 改写自身时（`execute-extended-command` 派发、lambda 归一、部分 mode 的 hack），同一次操作在 `hourly_gc_attrib.command` 与 `commands.name` 里**对不上**，两表按命令名 JOIN 会静默丢行；再叠加 TD-32，命令维度覆盖率实测只有约 **12%**（`<none>` 占 **88.1%**） | **未实施（低优先）**：修法是热路径改用 `(or (bound-and-true-p real-this-command) this-command)` —— 读 C 变量本身不分配，可守住零分配不变量，但须同步核对零分配守门用例的禁止符号词表（该用例用 `syntax-ppss` 剔除 docstring / 注释后只查代码区）。**收益有限**：等待输入期两者同为无意义值，故**不降低** `<none>` 占比，只解决「命令执行期 GC 归到被改写后的名字」这一少数场景 |
| TD-34 | **Org 文档里 `=\"…\"` 的多余反斜杠**：Org 的 code 标记是 `="<none>"=`，写成 `=\"<none>\"=` 会把反斜杠渲染出来；源头是把 elisp docstring 里的 `\"` 转义直接搬进了 Org | 文档渲染出多余反斜杠，读者会以为哨兵字符串本身带反斜杠，抄进 SQL / 查询里对不上 | **已修（2026-10-26）**：`docs/architecture.org` 2 处 + `docs/schema.org` 6 处（6 行 / 14 处反斜杠），全仓 `docs/` 下 `=\"` 已清零（复核：`grep -ro '\\"' docs/` 计数 = 0）；`.el` 文件中的 `\"` 是 elisp 字符串内的合法转义，**不在范围内**。修法：去掉反斜杠，`=\"<none>\"=` → `="<none>"=`（Org 的 code 标记本身不需要转义）。其余 `docs/*.org`（api / ui / operations）、`docs/adr/*.md` 与 `Readme.org` 实测 0 处 |
| TD-35 | **`--post-gc` docstring 的「唯一分配」措辞不精确**：原文称「`gc_ms` 的差值计算不可避免会产生一个 float，这是本函数唯一的分配（每次 GC ≤1 个）」；严格说是**两个中间 float**（减法的结果 + `* 1000.0` 的结果），只是 Emacs 31 的 immediate float 表示下通常不触发堆分配 | 措辞精度问题：读者可能据此以为「已明确只分配 1 个对象」，或反过来以为编译器保证零分配；不影响正确性，也不影响零分配守门用例（该用例断言「允许 float、禁止字符串」） | **不修（措辞级）**：严谨写法是「产生 1–2 个中间 float（immediate float 下通常不落堆）」。只改 docstring、不动函数体，任意一批文档同步时顺手修即可 |
